# Implementer dispatch recipe — the ONE canonical protocol

**Audience:** a dispatched implementer (a sub-agent spawned via a `.claude/agents/implementer-<model>-<effort>` cell, OR a fresh Claude Code instance launched by the operator). You have **NO prior conversation context** and you do **NOT inherit the orchestrator's memory or CLAUDE.md** — that is exactly why this protocol is a doc you are told to read. Read it in full, then execute your dispatched task / brief.

**Status:** the single source of truth for sub-agent + window implementer dispatch (the protocol that used to be re-inlined per prompt). Harness tooling, CHARC-owned. If anything here conflicts with your specific dispatch brief, the brief's *task scope* wins but these *disciplines* still bind — if they truly conflict, STOP and ask the orchestrator.

---

## 0. The shape of a dispatch
1. Read this recipe, the repo's **`CLAUDE.md`** (load-bearing — it carries the project gotchas + conventions), and your dispatch brief/task in full. Re-ground every file/line anchor against live code before editing (line numbers drift).
2. Work in an isolated worktree (§1).
3. Execute the task TDD, one red→green→commit cycle per logical change (§2).
4. **Run the FULL fast suite to GREEN BEFORE the review** (§2) — the §3 review must converge on a green diff (catches latent global-invariant tests early).
5. Run the Codex adversarial review to convergence and persist every response (§3) — when your brief calls for it (writing-plans / executing-plans / any code-shipping task).
6. Return a structured report to the ORCHESTRATOR as your final chat message (§4). Do NOT post to any role mailbox.
7. Honor the disciplines in §5.

## 1. Worktree (isolation)
- Create/use a worktree at **`<repo>/.worktrees/<name>`** — `git worktree add -b <name> .worktrees/<name> <base>`, where `<base>` is the base your brief specifies (a named commit / `BASELINE_SHA` if given, else `main`). The `<base>` arg is REQUIRED — without it `git worktree add` branches from current `HEAD`. Or reuse the existing worktree if your brief says the plan was committed there. The orchestrator owns main-currency at merge (it rebases your branch onto `main` before the `--ff-only` merge), so don't worry about `main` advancing while you work. **NEVER** use the Agent tool's `isolation: worktree` (it auto-creates a temp worktree outside this path, bypassing the editable-install verify, the cleanup script, and the gitignore coverage). The path `.worktrees/<name>` is binding — not `.claude/worktrees/`, not a repo-sibling.
- **Editable-install gotcha:** the `swing` package is editable-installed from the MAIN repo path, so a CLI entry point (`swing ...`) run from a worktree resolves the MAIN tree, not the worktree's code. For runtime/CLI verification from inside the worktree, run the package directly: PowerShell `$env:PYTHONPATH="."; python -m swing.cli <cmd>` / Bash `PYTHONPATH=. python -m swing.cli <cmd>`. **Pytest is NOT affected** (cwd-based discovery) — run `python -m pytest -m "not slow" -q` from inside the worktree and it tests the worktree's code.
- Leave the worktree intact at the end (the orchestrator rebases onto main + `merge --ff-only` + re-runs the suite on the merged head). Do NOT merge or push yourself.

## 2. TDD + commit conventions
- **TDD:** write the failing test → run it, SEE it fail (the right way) → minimal implementation → run it, SEE it pass → commit. One red→green cycle per logical change. Compute a regression test's assertion under BOTH the pre-fix and post-fix paths to prove it distinguishes (a test that passes under both is worthless).
- **Conventional commits** carrying the task id: `feat(area): Task X.Y — …`, `fix(area): Codex R1 Major 2 — …`, `refactor(...)`, `test(...)`, `style(...)`.
- **Commit with BARE git from the worktree cwd** — `cd` into `.worktrees/<name>` (your working cwd per §1) and run `git add` / `git commit` directly. Do **NOT** commit via `git -C "<worktree>" add/commit`: the harness permission allowlist covers the bare `git add`/`git commit` form but not the `git -C "<path>"` write form, so a sub-agent's `-C` commit gets permission-denied and you cannot land your own deliverable (dispatch friction 2026-06-17). If a git-write is denied, STOP and flag it (do not work around) — but the bare form from the worktree cwd is the covered path.
- **ZERO `Co-Authored-By`** — no co-author footer, ever. **No `--no-verify`. No amend** (new commit per fix). Before handoff, verify the WHOLE dispatch is trailer-clean: `git log <base>..HEAD --format='%H%n%(trailers)'` — every commit must show empty trailers. **If a forbidden trailer slipped in** (`Co-Authored-By`, or a prose `Word:` final paragraph git mis-parsed as a trailer): **STOP and flag it in the return report** — do NOT `--no-verify`, hide it, or silently hand off. The orchestrator resolves it at merge (amend + force-with-lease); the "no amend" rule is precisely why this is a stop-and-flag, not a self-fix.
- **Trailer-parse hazard:** keep the FINAL `-m` paragraph plain prose — a paragraph starting `Word:` (e.g. `Fixes:`) is parsed by git as a trailer and pollutes the zero-`Co-Authored-By` audit.
- **Ruff:** the lint gate is `ruff check swing/` (the `swing/` tree only). Introduce no new violations there. Test-file lint is out of scope unless your brief says otherwise; match each test file's existing style (≤100-char lines, local imports) so you add no new violation.
- **ASCII discipline:** user-facing strings flowing through stdout/CLI must be ASCII (Windows cp1252 crashes on `§ → ↔ ✓ ✗`, em-dash, fractions). pytest `capsys` hides this — prefer ASCII swaps in added code.
- **WRITING-PLANS phases commit the plan ONCE at convergence** (added 2026-06-14): a writing-plans dispatch is plan-only — write the plan, run Codex to convergence, then make a SINGLE `docs(plan): …` commit of the converged plan. Do NOT commit the plan once per Codex round (18-C's writing-plans produced 18 per-round commits — verbose history with no value). The converged plan is the deliverable; the round-by-round iteration belongs in `.copowers-findings.md`, not the git history.
- **Run the FULL fast suite BEFORE the Codex review — fix-to-green first (added 2026-06-15; operator-directed, the 18-F lesson).** After all task-commits land and BEFORE starting the §3 Codex loop, run `python -m pytest -m "not slow" -q` (the WHOLE fast suite, not just the task's tests) and fix any failure to green. WHY: per-task TDD runs only the task's tests; CROSS-CUTTING / global-invariant tests — cross-VM-consistency manifests, theme-token / no-raw-hex CSS contracts, schema-enum mirrors — are NOT exercised per-task and stay LATENT until a full-suite run. If that first full run happens only AFTER Codex convergence (the §4 end-of-run gate), a latent break forces a wasted fix + re-review cycle AND burns Codex rounds (the 18-F cost: the topbar VM-manifest + CSS-theme-token regressions surfaced post-convergence). Running it BEFORE means the review converges on a GREEN diff. This is IN ADDITION to the §4 end-of-run full-suite gate (which catches review-fix-introduced breaks) — the suite runs at BOTH points.

- **VERIFY THE BRIEF'S PREMISE BEFORE YOU BUILD ON IT — this is the highest-yield step in the protocol (banked 2026-08-06, CHARC-stated).** A brief's factual claims about the code are the ORCHESTRATOR's to check before dispatch and YOURS to re-check before authoring; **a fact belongs to the CODE, not to whoever last described it.** The Phase-21 boundary wave produced FOUR premise corrections at dispatch or authoring time — a "seven render sites" count that was eight, a "code-only default" that was a web-editable config field, a worked case quoted from an illustrative fixture rather than live data, and a "CHECK-widening tripwire" on an enum with **no SQL mirror at all** — and every one was cheaper where it was caught than where it would otherwise have surfaced. If a premise fails, **STOP and route it back**; a plan cannot un-cross a tripwire and an implementer cannot re-scope an arc. Corollary, learned six times in one week: **state what your grep PROVES, not what you infer from it** — a grep that names three files can only ever return three, and "which commits touch a mirror FILE" is not "which commits add to an EXISTING mirror."
- **ARM-FLAG / REPORT-ONLY WORK CARRIES A BOTH-MODES TEST REQUIREMENT (RD, 2026-08-06, attached at his own ruling).** When a feature ships behind a config arm flag defaulting OFF, a negative test asserting only *"it did not fire"* **passes under default-OFF regardless of the logic it claims to pin** — it would have silently voided the FTRE founding-case test, on the one test nobody re-examines. So: **every negative test asserts the COUNTERFACTUAL fields, and the founding/acceptance case runs BOTH armed and unarmed.** This is the vacuous-regression-test class arriving through a feature flag; RD attaches the requirement to any such ruling of his from now on, stated AT the ruling rather than discovered at review.

## 3. The WSL-Codex adversarial review (the load-bearing part — verbatim)
The MCP `codex` tools are dead in this environment; the working transport is the **WSL-native Codex CLI**. The copowers `adversarial-critic` Skill scaffolding may be **absent in a sub-agent** — if so, HAND-RUN the loop exactly as below.

**Review tier — model/effort by BLAST-RADIUS (added 2026-06-14, operator-concurred).** The review's model + reasoning-effort is tiered by the **blast-radius of a *missed* finding** — NOT implementer task-difficulty (a trivial-*looking* code change still has production blast radius). Two tiers, selected by the orchestrator (announced, vetoable) and passed in your dispatch; default by phase:
- **`strong`** (strong model + high reasoning effort) — **executing / ANY production-code review. NEVER tier this down** — it is the last automated net before merge; a missed major costs far more than the Codex saving.
- **`fast`** (cheaper model and/or lower effort) — writing-plans / doc / brief reviews (a plan/doc defect is caught downstream by the executing review + the gate).

**TIER NAMES REPOINTED to the operator's canonical profiles (operator-ruled 2026-07-30; landed 2026-08-03 in the post-21-B-merge window).** This recipe previously named `review-strong`/`review-fast`. Those profiles resolve to a **weaker model than the canonical ones** — `review-strong` → `gpt-5.5`, canonical `strong` → `gpt-5.6-sol` — so the recipe was pointing every *binding* review at the weaker of two available tiers. **Supersession by REPLACEMENT:** `strong`/`fast` are the names; `review-strong`/`review-fast` are RETIRED from this recipe (they still resolve, so nothing was broken meanwhile — but do not use them). The repoint was deliberately deferred until **no implementer was mid-convergence**, because renaming the tier an in-flight dispatch is already using changes the invocation underneath it — the 21-D self-modification class.

**Mechanism:** add `-p <tier>` to the `codex exec` command below — a Codex *profile* (`$CODEX_HOME/<tier>.config.toml`, layered over the base config). `-p`/`-m`/`-c` are confirmed on codex-cli 0.135.0. The actual model + `model_reasoning_effort` per tier live in those **operator-authored** profiles (one-time setup), so this recipe names the tier and never hard-codes a model. **Fallback (CORRECTED 2026-06-16 — the 18-H.4.1 effort=none gap):** if the named profile does not exist (e.g. a fresh sub-agent's `$CODEX_HOME` lacks the operator-authored profiles), OMIT `-p` **BUT explicitly pass `-c model_reasoning_effort=high`** — the profile's whole point is `effort=high`, and WITHOUT it the codex default is `effort=none` (the disqualifier that silently weakened BOTH the 18-F auto-review AND the 18-H.4.1 binding review). **NEVER let the binding review run at `effort=none`** — the `-p`-absent path forces `-c model_reasoning_effort=high` (the model may default below gpt-5.5, but the effort stays HIGH). Full model+effort tiering activates once the profiles are provisioned in the cell's `$CODEX_HOME`. **Tier the model/effort, NEVER the rigor:** the run-to-`NO_NEW_CRITICAL_MAJOR` loop + the full-diff final review on production code are unchanged. (The true safety net is the operator / live-DB witness, NOT Codex — which is *why* tiering the fallible intermediate filter is safe.)

**Liveness probe FIRST (the PATH prefix is REQUIRED — `~/.bashrc` does NOT reliably prepend node22 on its own):**
```
wsl.exe bash -ilc 'export PATH="$HOME/.local/node22/bin:$PATH"; codex --version'
```
Expect a `codex-cli <version>` line (0.135.0 at time of writing) — ANY successful version output proves liveness; don't hard-fail on a newer version. The check is that codex resolves the NATIVE binary, not the dead Windows npm shim. Use `codex --version` as the liveness proof, NOT `command -v codex` (which can resolve the shim `/mnt/c/.../npm/codex` → `node: not found`, or print empty even when codex runs). (Run these from your Windows shell — the Bash tool is Git Bash invoking `wsl.exe`. If you are already inside a WSL shell, drop the `wsl.exe bash -ilc` wrapper and run `export PATH=…; codex …` directly.)

**Staging (pilot frictions — do these or the call fails):**
- The worktree's `.git` is a *file* pointing at a Windows path WSL git CANNOT resolve, so **never let Codex run git**: pass **`--skip-git-repo-check`** and **pre-generate the diff from the WINDOWS shell** (Git Bash or PowerShell, run IN the worktree dir — NOT from WSL bash, which cannot resolve the worktree `.git`): `git diff -U8 <base>..HEAD > .codex-diff.txt`, where **`<base>`** is the baseline your brief gives you (the worktree's branch point / the plan-commit / an orchestrator-provided `BASELINE_SHA`) — i.e. the commit your work started from, so the diff is exactly YOUR changes. (Ensure your work is COMMITTED first — a clean `git status` — so no final uncommitted edit escapes the review.)
- **PRIMARY — pipe everything via STDIN inside the WSL+PATH wrapper; Codex needs to READ no repo files (everything arrives via stdin).** Redirect Codex's output to a FILE (never the terminal — its glyphs crash Windows cp1252 stdout). `<...>` below are placeholders:
  ```
  wsl.exe bash -ilc 'export PATH="$HOME/.local/node22/bin:$PATH"; cat <prompt>.md .codex-diff.txt [optional source-excerpt files] | codex exec [-p <tier>] -s read-only --skip-git-repo-check - > .codex-review-r<N>.txt 2>&1'
  ```
  (trailing `-` reads stdin.) Then append `.codex-review-r<N>.txt` VERBATIM into `.copowers-findings.md`, followed by YOUR per-finding adjudication for that round (so the file holds raw Codex output + your dispositions — the persist step). These `.codex-*` / `.copowers-findings.md` names are all gitignored, so they don't dirty the worktree for the §2 clean-status / trailer check. `cat` runs in WSL and reads `/mnt/c/...` fine, so you can cat straight from the worktree path and Codex never touches the filesystem — cwd/paths are irrelevant to CODEX (it reads stdin), though `cat` itself still needs resolvable paths (use absolute `/mnt/c/...` paths, or run from a WSL-visible cwd). A bare `cat | codex` copied into a Windows/PowerShell shell will fail or hit the dead npm shim — KEEP the `wsl.exe bash -ilc 'export PATH=…; …'` wrapper. **Never** pass the prompt as an argv arg (`codex exec "$(cat …)"` word-splits / dies on parens/special chars). (This is the path the recipe-doc review itself used — validated.)
- **FALLBACK — only when the diff/sources are too large to inline** and Codex must READ files itself: copy them into WSL **`$HOME`** (NOT `/mnt/c`, whose reads can be flaky under Codex's sandbox — and WSL `/tmp` ≠ Windows `/tmp`), run `codex` from `$HOME`, and reference the `$HOME` paths in the prompt. For more than one or two files, write a small **staging script** and run it (a long inline `-ilc '...'` with many files is var-expansion-fragile).

**REPO ACCESS for PRODUCTION-CODE review (added 2026-06-16 — the 18-H.4 lesson; LOAD-BEARING).** A pure DIFF-ONLY review is structurally BLIND to a defect whose correctness depends on UN-CHANGED surrounding code (a reference graph, closures, callers, an invariant in a neighboring file). **18-H.4:** a diff-only `review-strong` pass (3 rounds) MISSED that the shipped WinError-32 fix released only 1 of 3 strong refs to the resource — two un-changed ladder closures (`app.py` `_quote_hook`/`_bars_hook`, stored on app-lifetime caches) held the others → `gc.collect()` couldn't finalize → the fix was INEFFECTIVE; `codex-auto-review` with REPO ACCESS grepped the surrounding code and CAUGHT it. So for **production-code** review the binding reviewer MUST be able to read beyond the diff: EITHER give Codex repo read-access (point cwd at the worktree, `-s read-only` — it greps the surrounding code itself, as the 18-H.4 B run did on a repo-resolvable checkout) OR include the fix's reference-graph surrounding files in the stdin bundle (the diff PLUS the callers/closures/factory its correctness depends on). The pure-diff stdin form stays fine for SELF-CONTAINED changes (a new module, a pure function); it is INSUFFICIENT when correctness depends on the surrounding reference graph.
- **`codex-auto-review` ADOPTED as a COMPLEMENTARY second-eye on production-code arcs (2026-06-16, the 18-H.4 A/B).** Run it (repo-access, MATCHED-HIGH effort — `codex exec review --commit <pre-review-sha> -c model_reasoning_effort=high`; the 18-F `effort=none` disqualifier corrected) ALONGSIDE `strong` on production code. The 18-H.4 head-to-head: DISJOINT finding sets (A's 6 fix-internal majors vs B's single highest-severity production-effectiveness defect) → B is complementary (different blind spot), not a drop-in replacement. `strong` stays the iterative binding gate; a B `major`/`[P1]` is adjudicated + resolved-or-cited before merge. Re-assess B's long-term role (gating / advisory / redundant-with-repo-access-A) after a few arcs with both in place.
  - **WSL-worktree invocation (banked 2026-07-04; CHARC-concurred — the 19-D/19-E finding).** `codex exec review` needs git to resolve the checkout, and a worktree's `.git` is a Windows-absolute-path FILE that WSL git cannot resolve (`git rev-parse HEAD` → "not a git repository"), so `--base`/`--commit`/`--uncommitted` all fail from a raw worktree cwd. **The working form:** export `GIT_DIR` + `GIT_WORK_TREE` explicitly so WSL git resolves the worktree, then run `codex exec review` from inside it — `wsl.exe bash -ilc 'export PATH="$HOME/.local/node22/bin:$PATH"; export GIT_DIR=/mnt/c/.../.git/worktrees/<name>; export GIT_WORK_TREE=/mnt/c/.../.worktrees/<name>; cd $GIT_WORK_TREE; codex exec review --base <diff-base> -c model_reasoning_effort=high > .codex-autoreview.txt 2>&1'`. Get `GIT_DIR` from `git -C .worktrees/<name> rev-parse --absolute-git-dir` (translate `C:/…` → `/mnt/c/…`); `<diff-base>` = the worktree's executing-diff base (the plan/BASELINE commit your work started from). **A one-time `git config --local core.autocrlf true` is LOAD-BEARING on a Windows-checked-out worktree (the 19-D belt, 2026-07-04):** WSL git's eol handling disagrees with the Windows checkout (Git-for-Windows sets `autocrlf=true` in SYSTEM config; WSL git does not), so it flags the ENTIRE tree as CRLF-modified and codex's INTERNAL git computes a whole-repo GARBAGE diff (CLAUDE.md + every doc, delete+re-add) — the verdict is MEANINGLESS despite exit 0. **`GIT_CONFIG_*`/`-c` env does NOT reach codex's internal git** (verified 2026-07-04: a plain `git status` honors the env, but `codex exec review` still saw the 2397-file mass-diff) — the fix MUST live in the repo `.git/config`: run `git config --local core.autocrlf true` ONCE (matches the effective Windows system value; local-only, untracked, reversible via `--unset`). This cleans plain WSL `git status` — **but the 19-D belt found `codex exec review` STILL surfaced the mass-diff in its own trace even with a clean status** (codex's internal diff path bypasses the config). So do NOT trust a bare "no issues" verdict: TRUST it only when it ENGAGES the actual changed files/mechanisms (names the real change). **The most robust complementary second-eye on a Windows worktree is a `codex exec -s read-only -c model_reasoning_effort=high` COLD-AUDIT that reads the changed files DIRECTLY (no git-diff dependency)** — the form that ran cleanly + focused for 19-D; `codex exec review` stays a best-effort add-on, and the stdin-bundle `strong` (Windows-pre-generated diff) remains the unaffected binding gate. Redirect to a gitignored `.codex-*` file (Codex glyphs crash cp1252 stdout). This SUPERSEDES the earlier "run canonical from the MAIN checkout post-merge" idea — pre-merge canonical on the worktree is available and strictly better. (If `GIT_DIR` still misbehaves, the stdin-bundle `strong` with reference-graph files remains the fallback.)

Use the cold-audit form (`codex exec -s read-only -c model_reasoning_effort=high`, reading the changed files directly, no git-diff dependency) as the DEFAULT worktree invocation, not as a fallback. **Why this now matters more than a footnote:** CHARC's standing ruling (charter §2.9, 2026-07-28) makes `codex-auto-review` a REQUIRED gate on production-code arcs — so an implementer who hits this wall and quietly skips the step silently drops a mandatory gate. If your first invocation fails, switch forms; never skip.

  - **(21-B, 2026-07-30 — CHARC-investigated) MANDATORY PER-ROUND BANNER ASSERTION. A ROUND THAT FAILS IT DID NOT HAPPEN AND MUST NOT COUNT TOWARD CONVERGENCE.** The rule above named a discipline without naming a check, which is why it kept recurring; this is the check. **Codex fails silently in two ways that `exit 0` cannot detect:** an **unrecognised `-p` profile name runs at reasoning effort `none`** (verified still true at codex-cli 0.146.0) — `effort=none` being the exact disqualifier this section forbids for a binding review — and, observed at 0.135.0, **an API-error run returned exit 0 while producing nothing but `ERROR` lines.** Exit status is therefore NOT evidence that a review happened. **Both are plainly visible in the output file.** After EVERY round, before counting it: **(1)** assert the banner's model is the one you intended — **`gpt-5.6-sol` for `strong`, the binding tier** (the RETIRED `review-strong` resolved to `gpt-5.5`; if you see `gpt-5.5` on a binding review you are on the retired profile and the round does not count); **(2)** assert `model_reasoning_effort` reads **`high`**; **(3)** `grep -c '^ERROR'` the output file — **anchored, and the anchor is LOAD-BEARING** (see below); **(4)** assert the **`tokens used` FOOTER is present**. If the model is wrong, or effort reads `none`, or a `^ERROR` line is present, or the footer is absent — **re-run with a corrected invocation; the round does not count.** **Record the asserted model + effort + footer per round in `.copowers-findings.md`** so the orchestrator verifies convergence from the transcript rather than from a claim.
    - **WHY THE FOOTER, and why the banner alone was two-thirds of a guard (added 2026-08-06, CHARC-endorsed).** The banner is an OPENING sentinel: truncation removes the END of a file, never the start, so the banner survives every truncation BY CONSTRUCTION and can certify nothing about completion. A verdict line is response text that streams BEFORE finalization, so a mid-write read can contain banner PLUS verdict while the round is still running or dies afterward. **The `tokens used` footer is the only line written AT completion** — banner proves the round STARTED, footer proves it FINISHED, the ERROR grep covers the middle. Three assertions, three failure windows, no overlap. The door that makes the third window reachable in practice is a broken wait — see the `pgrep` hazard below.
    - **THE ANCHOR ON THE ERROR GREP IS NOT PEDANTRY (found 2026-08-06, the coverage_gaps arc).** A bare `grep -c ERROR` returns **5** on a round that was entirely clean — every hit was **CLAUDE.md prose the model echoed after reading repo files**. Codex diagnostics are LINE-INITIAL, so `^ERROR` is the gate and it reads 0 on those same rounds.
