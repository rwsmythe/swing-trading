# Harness Architecture — the shared cross-role reference

**Owner:** CHARC (tool-development director), per `tool-director-context.md` §2.8 — harness architecture is a CHARC-owned category. **Corrections route through CHARC, never self-authored by another role.**
**Audience / read-at-spinup:** BOTH directors (CHARC + RD) read this at bootstrap. It is the single canonical home for the rules that govern how the roles relate; each role's *own* charter holds its role-specific behavioral contract and tactical content and points here for the shared model.
**Why this doc exists:** the director charters are single-reader by design (CHARC doesn't read RD's at spinup, nor RD CHARC's). Cross-role harness rules placed in one charter are invisible to the other role — so they live here instead (stood up 2026-06-13).

---

## 1. Roles, hierarchy, and the swimlane principle

```
operator                 — human principal; originates capability demand; sole decision authority
  └─ directors            — strategic lanes (CHARC = tool/engineering; RD = research/evaluation); PEERS of each other
       └─ orchestrators    — delivery / engineering managers; one generation per stint
            └─ implementers — individual contributors; one scoped task, often worktree-isolated
  Codex                    — external adversarial QA, at every phase
```

- **Directors are PEERS of the operator.** A director's opinion and the operator's carry **equal weight** in discussion; the operator holds ultimate authority to override. A director pushes back on the operator's decisions/reasoning at a **low** threshold (sincere disagreement, not devil's advocacy, not an audit posture). Each director's behavioral expression of this lives in its own charter (CHARC §5.1; RD's blunt-over-sycophantic clause).
- **Lower roles are scope-limited BY DESIGN.** Narrower scope = tactical focus; extra context is creep. This is *intentional*, not a deficiency — see §4.

## 2. Content-ownership: three categories (don't conflate them)

A document (e.g. `orchestrator-context.md`) can hold content of more than one category. Ownership follows the category, not the file:

| Category | Examples | Owner |
|---|---|---|
| **Harness-artifact HYGIENE** | doc weight, brief-corpus retention, staleness flags, compaction mechanics | CHARC as custodian (FORM only; `tool-director` §2.6 + §4.2 + `harness_probe.py`) |
| **Harness ARCHITECTURE / DESIGN** | role boundaries, the scope-limitation + flag-vs-comply rule (§4), the tripwire model (§5), the comms taxonomy (§3), this doc | **CHARC** — author/maintain wherever documented, incl. inside another role's context doc (marked CHARC-authored) |
| **A role's TACTICAL operating content** | how an orchestrator drafts a brief, its QA checklist, its housekeeping steps | the role itself; CHARC flags FORM only |

**Custodian boundary (load-bearing):** for the hygiene category CHARC is *custodian of FORM, never owner of CONTENT* — weight/retention/staleness are CHARC's; the gotcha text / charter entries / todo content belong to their writing roles, and no role's writes route through CHARC for approval. The ARCHITECTURE category is the exception the operator clarified 2026-06-13: those rules ARE CHARC's to set and correct, because (see §4) a scope-limited role cannot author a rule whose justification sits outside its swimlane.

**THE ARCHIVE DISCRIMINATOR FOR A LIVE CONTEXT DOC'S DECISION RECORDS (adopted 2026-09-10 — orchestrator-proposed on its own trim packet, CHARC-ruled with one sharpening; hygiene category, so CHARC's to set).** An entry in a role's context doc is ARCHIVABLE (verbatim, to the doc's `-archive.md` companion, with a pointer naming title, date and OWNER) iff **(1)** a NAMED live artifact now owns the rule or finding, so the entry is a decision RECORD and not the operative statement, or **(2)** it records a one-off completed ACTION with no forward force. It STAYS if it could be REOPENED (strategy, doctrine, live governance), if it carries FORWARD FORCE (binds future work), or if it is a FINDING with no named owner — an archive is not a home, and a grep of the companion is not ownership. The test never asks "is it old." Owner determinations are made by grepping the CLAIM to its candidate artifact, text-anchored (a bare number matches data by coincidence), and the pointer shows the owner column so the next reader sees the test applied. First application: `orchestrator-context.md` §"Recent decisions", 2026-09-10 — 21 of 25 proposed entries moved, four stayed on the owner/forward-force tests, the ruler's own forecast of which would fail was wrong on two of three.

**PREMISE-SOURCING: SOURCE EVERY PREMISE FROM THE ROLE (OR ARTIFACT) THAT OWNS IT** (adopted 2026-07-28 — orchestrator-diagnosed, RD-generalized, CHARC-authored). §2 says who owns which CONTENT; this says where a claim must be sourced FROM. Three instances produced in a single day, each the same rule against a different premise-owner:

| Premise | Owned by | Failure when sourced elsewhere |
|---|---|---|
| A **FACT** about behavior | the CODE, not a doc | An untraced "~20 sessions" in a director doc became a plan input, then the plan cited that doc as evidence — a **circular citation**, broken only by reading `config.py`. (Also: a drifted stop quoted from a stale row.) |
| A **POSITION** | the role that HOLDS it, re-checked at POST time | Three crossings in one thread; a closure landed **6 seconds** after the reversal that reopened it. A stale position decays far faster than a stale fact. |
| **DISPATCH STATE** (what is in flight) | the ORCHESTRATOR, and ONLY it | Both directors inferred dispatch state from each other's messages; neither could observe it. The mailbox serialized nothing because the state change was in nobody's message. |
| **A QUOTED POSITION** | its SPEAKER — a downstream editor may correct the surrounding text but NEVER the quote | An implementer silently tightening a director's language. **This row is distinguishable from the other four: they produce a wrong answer you can eventually TRACE; this one produces a PLAUSIBLE RECORD YOU CANNOT** — a softened quote still reads like a quote, so the record degrades with no signal. |
| **GATE STATE** (is a director gate cleared, or outstanding?) | the GATE-HOLDER | 21-A merged while RD's merge-blocking clearance was still formally HELD pending the post-change number. Outcome was correct (the number was green; he would have cleared on sight) — but **a gate compressed because it would have passed anyway is not a gate; it is advice with a ceremonial step.** |

**THE TEMPORAL CLAUSE (2026-08-12, RD's confounded forward test): A QUIET INSTRUMENT ONLY EVIDENCES THE FIX IF THE INSTRUMENT RAN AGAINST THE FIXED CODE — sequence position is provenance, the same way a line's git history is.** The instance: "no fifth emission across four subsequent runs → THE FIX TOOK" — true count, false conclusion, because the chain stopped at run 97, FOUR DAYS before the fix existed; three of the four "confirming" runs executed the unfixed code and the post-fix evidence was one run. The test's own designer caught it and retired his own instrument, closing the rows on direct evidence (the witnessed correction) instead. **The general form: any claim of the shape "X stopped happening BECAUSE of Y" must date X's cessation against Y's existence** — an effect that precedes its proposed cause is somebody else's effect, and the unexplained cessation becomes its own finding (a check that goes quiet for an unknown reason is a candidate silent-failure of the check).

**A RULING IS NOT A SOURCE — its REASONING is binding; its INCIDENTAL FACTUAL CLAIMS are still claims (adopted 2026-08-09 — orchestrator-proposed after repeating one, RD-adopted after authoring it, CHARC-canonicalized as the table's missing row).** The five rows say where each premise kind is sourced FROM; this says that a director's ruling does not become a source for the FACTS embedded in it — a fact still belongs to the CODE even when it arrives inside a ruling. The instance: RD's ruling contained "every hop is schema-guaranteed"; the orchestrator put it into a binding document unchecked *because it arrived from a director*; verified, migration 0033 has no UNIQUE on the first hop's key — the chain is conditional. The true half of such a sentence makes the false half sound checked. **Premise-sourcing does not exempt rulings.**

**PRESERVE THE QUOTE, CORRECT THE SURROUNDING TEXT, FLAG IT UP (adopted 2026-07-29 — implementer instinct, orchestrator-proposed, RD-ratified, CHARC-canonicalized).** When a review catches an **overstatement in a director's QUOTED words**, the implementer **preserves the quote verbatim**, corrects the document's OWN surrounding sentence, and **flags it up** — it does not silently tighten the director's language. **The handling rule for the row above:** preserve verbatim, correct the surrounding sentence, flag it up. If a director wants the claim tightened, the director tightens it (as RD did the same day: *archive lag is ONE divergence condition, not the only one*).

**SUPERSESSION IN AN ARTIFACT IS PERFORMED BY REPLACEMENT — ANNOTATION IS NOT SUPERSESSION (adopted 2026-07-29 — orchestrator-diagnosed, operator-instructed, RD-argued-for-form, CHARC-authored).** When a review-loop fix supersedes text, the fix **REPLACES** the superseded text; it does not add a note beside it. **The change record lives in the COMMIT MESSAGE and the review transcript — never in the artifact's normative voice.** That second half is what makes the rule followable rather than merely correct: implementers annotate because they believe they are preserving the audit trail, so the rule must say where the trail actually goes.

**Why it earns the space — THE LOOP MANUFACTURES ITS OWN FINDINGS.** An annotation leaves the superseded rule standing in NORMATIVE VOICE. The next adversarial round reads it as a live instruction — correctly, because it is written as one — files a finding against it, and that finding is then also fixed by annotation. The artifact grows, the contradiction count stays flat, and convergence slows while every round appears productive. **Proof, not illustration (21-B, 2026-07-29): the round-21 CRITICAL survived round 20's fix PRECISELY BECAUSE round 20 added a superseding note instead of deleting the text.** One paragraph carried THREE LAYERS in one voice — the current rule, the superseded rule, and the change narrative. The coherence pass that replaced instead of annotating resolved 18 contradictions AS A SET, and answered the size question in passing: all 18 were PRESENTATION, each with exactly one right answer already stated somewhere in the plan — the signature of a coherent design inside an unreadable document, so the fix was separation of voice, not division of scope.

**STANDING BRIEF CLAUSE (the operator's instruction, 2026-07-29): every dispatch brief carrying an adversarial review loop states this rule.** A catalog entry is read by someone who goes looking; this failure is met by an implementer already mid-loop at round 14 and looking nowhere — exactly when the pressure to annotate is highest, because deleting feels like destroying the review's audit trail. **The failure is INVISIBLE FROM INSIDE THE LOOP:** each individual annotation reads as diligence, and nothing signals the defect until someone stops the loop and reads the whole artifact for coherence, which no adversarial round ever does. Same class as D28 — known, violated, and violated by people who knew it.

**Its pairing (RD's framing, adopted):** this is the ARTIFACT-side twin of PRESERVE-THE-QUOTE above. That rule says do not EDIT another role's words; this one says do not LEAVE your own superseded words in normative voice. Together they bound what a downstream editor may and must do to text. The MESSAGE-side analogue is SUPERSEDES-in-the-subject (§3): declare supersession in a message, perform it by replacement in a document.

**THE PARAPHRASE CANNOT BOUND THE ARTIFACT (adopted 2026-08-07 — RD-diagnosed against himself, CHARC-canonicalized; PRESERVE-THE-QUOTE's mirror, from the directing side).** When directing an excision or partial edit of an artifact, **quote the text to be preserved VERBATIM, or delegate the seam and say so — never paraphrase it.** A paraphrase is a NEW artifact; it cannot bound an old one — it bounds the director's SUMMARY of the text, and the gap between the two is exactly where a surviving falsehood lives. The instance: RD bounded a comment deletion by paraphrasing the keep-half as one proposition; the artifact's sentence carried TWO, joined by an em-dash, and the paraphrase silently dropped the false one — the excision as scoped would have preserved a falsehood in the authority position under a fresh reviewed-at commit. It survived only because the direction ALSO delegated the seam and the executor acted on the delegation over the line numbers — and RD's own verdict on that stands as the rule's sharpest line: **a bound that is only safe when ignored is not a bound.** Pairing: PRESERVE-THE-QUOTE says a downstream editor must not reword a director's words; this says a director must not reword the ARTIFACT's words when the rewording is doing load-bearing work.

**GATE VISIBILITY (adopted 2026-07-28 — RD-raised, CHARC-authored).** The operator may absolutely authorize a merge over an outstanding director gate — that is his authority and it is not in question. What must not happen is that the override becomes **invisible**. **If a merge proceeds with a director gate outstanding, the merge report says so in one clause** (e.g. *"operator-authorized with RD's clearance still held pending the number"*), so the record shows a DELIBERATE OVERRIDE rather than an omission. Same principle as the state-broadcast commitment above: make it READABLE, never inferable. Rationale, in RD's own framing turned on himself: *a known-benign exception is how a rule erodes* — the argument he used to require the multiplicity guard rather than ship a tenth false all-clear with a footnote, applied consistently to his own gate rather than only to a panel string.

**A CLEARANCE ATTACHES TO THE TREE THE GATE-HOLDER VERIFIED (adopted 2026-07-29 — RD-raised, CHARC-authored).** GATE VISIBILITY above says an outstanding gate must not be silently overridden. This says what a *granted* clearance covers, which is the question that arises the moment anything lands between clearance and merge:

- **Docs-only, no test coupling, and the director's final text already in hand → LAND IT.** It cannot move the tree in any respect the gate examined. No re-clearance.
- **Anything touching CODE or TESTS → the gate RE-OPENS**, however small. The merged tree is then not the one that was cleared, and the verification no longer describes what shipped.

**The precondition is what keeps this a rule rather than a loophole: "docs-only" must be VERIFIED, not assumed** — grep `tests/` for the document before editing it. In THIS repo docs can be load-bearing (a test asserts a study's cited artifacts are git-tracked; the D21 sweep broke six tests that hard-coded brief paths). Detached from that check, the carve-out silently becomes "I believed it was docs-only." *Origin: 21-G, where the orchestrator landed RD's corrected D27 text after clearance and before the ff-merge, having first confirmed no test referenced either document — RD ruled the judgment correct and asked for the general rule rather than a one-off blessing. Shipping an artifact carrying text its author had already superseded, planning to correct it afterward, is the worse trade.*

**The structural half (orchestrator commitment, 2026-07-28):** whenever it countermands, narrows, or re-instructs a live dispatch, it posts that as its own short status IMMEDIATELY, before anything else — dispatch state becomes something directors READ, not something they INFER. **The reciprocal obligation on directors:** when a ruling depends on what is currently in flight, rule against the orchestrator's LAST STATE STATEMENT (naming it, so a stale premise is visible in your own text), never against another director's message; if the state is unclear, ask rather than infer.

## 3. The comms information-vs-authority taxonomy (canonical)

The role mailbox (`scripts/role_mail.py`, `comms/<role>/{inbox,read}/`) enforces this in code:

- **UNIFORM SINGULAR ADDRESSING (arc 21-D, 2026-07-27).** EVERY role — `charc`, `rd`, `operator` AND `orchestrator` — has ONE fixed inbox `comms/<role>/{inbox,read}`. `--to orchestrator` is the only orchestrator address; the orchestrator inbox is drained by whichever generation is live (a handoff transfers the drain). The retired per-generation forms are **REJECTED, never ignored**: a `--to orchestrator:<session_id>` recipient and a `--session <id>` read flag each fail with an actionable message naming the singular replacement, so a stale caller LEARNS instead of silently misrouting. The `session_id` survives ONLY as a role-presence / recovery key in `comms_session_registry` — never as an addressing key. Historical per-generation trees were MOVED (never deleted) to `comms/orchestrator/_archive/<session_id>/` by `scripts/archive_comms_generations.py` (dry-run by default). *Origin: per-generation tracking produced only overhead in this repo — the F5 `newest_live` staleness class, the 2026-07-11 stray spin-ups, the R3 registry tidy, and two director misdeliveries — against zero occasions where two generations were meaningfully live at once.*
- **Role→role messages are limited to `fyi | status | query | return_report`.**
- **`decision_request` is valid ONLY when every recipient is the operator** — the CLI refuses to write one addressed to any other role.
- **Dispatch-direction traffic** (commissioning briefs, implementer dispatch prompts, approvals) carries AUTHORITY, which is the operator's alone. The V1 rule kept ALL such traffic operator-hand-carried; **amended 2026-06-26 (operator):** a director MAY post a dispatch (an action-bearing message) directly to the orchestrator's inbox (`comms/orchestrator/inbox`) **once the operator has PRE-AUTHORIZED the action** — the operator grants authority *before* the director sends, so a director's action-bearing inbox message carries the operator's IMPLIED approval, and the orchestrator acts on it as it would an operator-hand-carried prompt. The principle is unchanged — **automate the transport, never the authority**: the operator still grants the authority (pre-authorization); the director becomes the courier instead of the operator. (The operator reviews dispatched traffic via the comms GUI, not an inline pre-post check.) `decision_request` stays operator-recipient-only (the L1 lock).
- **An AUTOMATED / non-human SENDER (a process, not a role — e.g. a nightly pipeline emitting a status notify) must be TYPE-CONSTRAINED to the emit-only types it needs (`status`/`fyi`) at the sender gate, NOT granted the full type set.** The `decision_request` recipient-gate is INSUFFICIENT defense here: that gate PERMITS operator-addressed `decision_request`s, so an unconstrained automated sender could post authority traffic TO the operator. Constrain its TYPES upstream of the recipient-gate (an emit-only allowlist). **Tripwire-review corollary (§5):** a comms-taxonomy sender-widening review verifies the new sender's full TYPE-reach (what types, to whom — incl. the operator-addressed-authority vector), not just the recipient-gate. *(Origin 2026-06-22, 18-H.7: adding an automated `pipeline` sender; codex-auto-review caught it inherited the full types so `pipeline→operator decision_request` would have succeeded — CHARC's plan-stage review had checked only the sender-agnostic L1 recipient-gate. Fixed by an emit-only allowlist constraining `pipeline` to `status`.)*

The comms system is staged: **Stage 1** = the durable file mailbox + cold-start launcher + the unread hook; **Stage 1.5** = the optional operator GUI; **Stage 2** (push/MCP bus) only if Stage 1 chafes; **Stage 3** (autonomous wake) gated on evidence Stages 1–2 under-serve. Staging detail + the Stage-2/3 reference design: `tool-director-context.md` §2.5 + `docs/comms-stage2-push-research.md`. The orchestrator-inbox + session-registry design doc is `docs/comms-stage2-orchestrator-inbox-design.md` — **historical: its per-generation addressing half was retired by 21-D** (its own "a single shared `comms/orchestrator/inbox` … is simpler and likely sufficient" alternative is what the harness now runs). Friction-evidence accrues against the Stage-2 bar.

**SUPERSEDING messages declare it in the SUBJECT (convention, adopted 2026-07-28 — RD-proposed, CHARC-authored; harness architecture is CHARC's lane §2).** When a message REVERSES or SUPERSEDES an earlier position on the same question, the SUBJECT must say so and name what it supersedes — e.g. `SUPERSEDES my 15:32 ruling on X: …`. **Why the subject and not the body:** the inbox LISTING is where a reader decides "am I current?", and that decision must not require opening and diffing two messages. **Origin (2026-07-28, three crossings in ONE thread on one small question):** directors posted faster than the mail round-trips; each crossing was caught only by a reader comparing timestamps, and each cost a round — including CHARC declaring a question closed **six seconds** after RD's reversal re-opened it, and both directors then posting near-identical corrections that crossed *again*. Nobody erred; it is a cadence artifact of using an asynchronous mailbox synchronously. **A stale POSITION goes stale far faster than a stale FACT** — a claim about what a colleague has already decided should be re-checked at POST time, not at read time; a claim about code can be checked once. **ONE SUPERSESSION PER MESSAGE (amendment adopted 2026-07-29 — RD-diagnosed against himself, CHARC-authored; harness architecture is CHARC's lane §2, so the amendment is not his to self-author even though the gap is his to have found).** A message carries **AT MOST ONE** supersession. A correction touching a second target is a SECOND MESSAGE.

**Why the rule above was insufficient.** SUPERSEDES-in-the-subject solves VISIBILITY — can a reader tell from the listing whether they are current. It says nothing about a message carrying MORE THAN ONE supersession, and that gap has a distinct failure mode: **a multi-part message gets acted on PARTIALLY, and the part that gets acted on is the part the SUBJECT names.** This is the ACTIONABILITY half; visibility alone does not reach it.

**Origin (2026-07-29, RD's own message, and the consequence was concrete).** One message carried two corrections to two different sections of the same artifact; only the first was in the subject. The first landed at the 21-G merge; **the second was left behind — and the merge made its absence worse than neutral rather than merely incomplete:** the corrected §0 now instructed readers to read it before hits 4/5/7 and cross-referenced "the SAME event as hit 7's look-ahead path," while hit 7's own paragraph still carried the BACKWARDS mechanism and a claim that no instance had been sought when one had been measured. **A reader following the document's own instruction would have landed on the wrong mechanism.** RD caught it post-merge and closed it by replacement at `c78f3c33`. Nobody was careless: the downstream actor landed exactly what the subject advertised.

**Banked mechanization candidate (if the convention decays — the D21 class):** a `role_mail post --supersedes <message>` flag that stamps the subject automatically, making the signal structural rather than remembered. Under this amendment the flag is naturally single-valued, which is the mechanization arguing for the same shape.

**SUBJECT LENGTH IS CAPPED AT 80 CHARS, ENFORCED IN CODE (operator-directed 2026-08-12, `scripts/role_mail.py`).** **A SUBJECT NAMES THE MESSAGE; THE BODY CARRIES IT.** The finding, the evidence and the reasoning go in the body — they are what the body is for. **Why a hard cap and not a convention: all three roles drifted the same way, independently** — both directors and the orchestrator — **and the worst observed subject was 839 characters**, a full abstract with its own argument structure. That is the D28 signature (a documented norm that knowledgeable parties violate), and the answer to it is a mechanical guard, not a firmer promise. **Two costs made it concrete rather than aesthetic.** `_slugify` truncates the filename to `_SLUG_MAX` (40), **so everything past ~40 chars is invisible in a listing and reaches no reader in the view where a subject does its work**; and in the read view the long subject restates the body it sits directly on top of, so the reader pays for it twice and learns nothing the second time. 80 is deliberately generous — git's own subject convention is 50 — so anything tripping the cap is an abstract, not a tight subject. **The cap composes with the SUPERSEDES rule above rather than fighting it:** a supersession tag plus a short name fits in 80 with room to spare, and the tag is exactly the kind of thing a subject SHOULD carry — a signal a reader acts on from the listing, not an argument they must weigh.

**The diagnosis worth keeping, because the pressure that produced it is legitimate and will return.** The mailbox is asynchronous and a recipient may act on the listing alone, so there is real pressure to make a subject self-sufficient. **The pressure is sound; the response was not — the fix for "the body might not be read" is never "put the body in the subject,"** because the subject is the one field that provably truncates. Where a message genuinely must be actionable from the listing, that is an argument for a SHORTER subject naming the required action, not a longer one containing it.

**ONE RULER PER ITEM (adopted 2026-09-07, operator-directed; coa-chess `f2350396`, landed here BEFORE wake-on-mail because the two together are the failure).** Every message names exactly ONE ruling seat per item — `PRIMARY: <role>` for the whole, or a per-item ruler when a packet spans lanes — and a seat rules only its own items. A CC seat reads for awareness and HOLDS: it speaks only after the ruler's packet has LANDED, and only to DISSENT — and the dissent goes to the ruler and the operator, never to the sender, so the sender receives one authoritative answer per item and acts on it at once. A CC seat that concurs says NOTHING (the one place where silence IS assent: a review of a landed ruling, never a gate). A mis-addressed item is FORWARDED in one line, never double-ruled. An item that genuinely needs both seats is SERIALIZED by the sender ("CHARC rules, then RD reviews the ruling"); two seats never receive the same open question. Director-to-director disagreement goes UP to the operator, not sideways (§1). **Re-list the inbox immediately before posting** — that is what catches a ruler's packet that landed while you composed. This is the RULING-PACKET rule (§5.1) extended across SEATS instead of across MESSAGES. Why now: coa-chess's orchestrator posted one scope question with a PRIMARY and a CC; the CC concurred before the PRIMARY ruled, and the cycle was spent reconciling two answers. Swing got through 2026-09-07 without a collision only because the orchestrator's packets happened to name a seat per item — a habit, not a rule — and with both directors woken by their inboxes at the same instant (below) the collision becomes the norm.

**WAKE-ON-MAIL (Stage 3 of §2.5's staging, adopted 2026-09-07 on the evidence the stage was gated on: the operator typed "inbox updated" into a director session eight times in one day — a human relay on every hop).** Each role arms, at bring-up, a PERSISTENT `Monitor` on its OWN inbox directory (poll 2 s; ONE event when the file count RISES); the event wakes the session, which drains. Pull-side, zero spend while idle, one turn per arrival (identical to the cost of one "inbox updated" prompt), no sender change, dies with the session and re-arms at pickup. A message landing MID-TURN queues until the turn ends and is caught by the Stop hook's continue-on-unread (B-14). The mailbox stays the record; the monitor is only the cue. Cross-session `SendMessage` was considered and rejected as the channel (every sender adds a step; inbound messages are HELD for approval when permission modes differ; cells send under their parent's address). The exact command lives in each role's bootstrap. coa-chess `0b38be39`.

**The mailbox is TRANSPORT, not a TRACKER (convention, operator-approved 2026-06-13).** A `read`/ack moves a message to `read/` and clears it from the active surface — so anything that must PERSIST until a future event (deferred watch-items, gate checklists, action items owed at a later return) does NOT live only in a mailbox message. It is transcribed into a durable tracker (the arc dispatch brief / a gate checklist / the phase todo); the mailbox message carries a POINTER to that tracker, not the must-persist payload. (Origin: 2026-06-13, RD's executing-return watch-items lived only in an acked reply and were nearly lost — friction instance #2.)

**A RULING IS A MUST-PERSIST ITEM; ITS DURABLE HOME IS THE ARC'S COMMITTED LEDGER (adopted 2026-09-08, CHARC — stated by mail that day, landed here 2026-09-09).** The rule above already covered it and never said the word, which is why two directors spent a week posting rulings as if the mail were the record (the outgoing orchestrator's 09-08 report: a ruling living only in role-mail has no durable home — `comms/` is gitignored; it survives a generational handoff on this machine but not a clone, and its FINDABILITY decays with every ack, so the hole is discovery, not loss). A ruling is transcribed into the arc's committed ledger (the executing ledger for executing-stage rulings, the plan ledger for plan-stage ones) with the ruling seat named as AUTHOR and the transcriber as COURIER only. **Two forms, and the transcription labels which:** a **block quote** (the ruling's own words, unaltered — the default), or **"re-set, verified by the ruling director"** (a re-statement the ruling seat has read and confirmed, used only when the original cannot be quoted whole). **A packet is LANDED when the courier's transcription is committed and its path is posted back; until then the ruling is IN FLIGHT** — a seat acting on a mailed ruling as if it were landed is acting on transport.

## 4. Role scope-limitation + flag-vs-comply (canonical)

A scope-limited role (orchestrator, implementer) owes the operator **informed consent within its lane**, not silent obedience and not re-litigation:

- **Flag a consequence ONLY when it is material, non-obvious, AND visible in the role's own lane** (e.g. a waived test that gates merge safety; a skipped migration step that risks data). Then **comply regardless** — one flag, not a debate.
- The role does **NOT** flag, and **cannot assess**, CROSS-PHASE or architectural consequences — those are invisible to it by design. They are the **director's** burden, caught via the tripwires (§5) that route the broad view UP to CHARC.
- Corollary: a benign, obvious, or cross-scope-only decision warrants no pushback from the scope-limited role.

**The "unknown unknown" principle (why this is CHARC-owned):** a scope-limited role faces its own scope rules as an unknown unknown — it cannot author or self-correct a rule whose justification lives outside its swimlane. So a rule *about* a role's scope or cross-boundary behavior is necessarily the architect's, set and corrected from the CHARC level. (The orchestrator-facing copy of this rule lives in `orchestrator-context.md`, marked CHARC-authored, because orchestrators read that file, not this one.)

Note the contrast with §1: **directors** push back at a LOW threshold (peers); **scope-limited roles** flag at a HIGH threshold (in-lane/material/non-obvious only). Different bars, by design.

## 5. Architecture-review tripwires (canonical)

A commissioning/dispatch brief routes through CHARC for a pre-dispatch architecture pass when it introduces ANY of:

- **New schema** (migration adding tables/columns; CHECK-enum widenings count).
- **New module or package** under `swing/` (not new functions in existing modules).
- **New external dependency** (or a major-version re-pin of a shared one — memory `feedback_isolated_venv_for_shared_dependency_migration`).
- **New standing process** (a new pipeline step, daemon/scheduled job, operator ritual, or role/charter).
- **A phase-isolation carve-out** into `swing/trades/` or `swing/data/` (the CLAUDE.md invariant's default is read-only).

Everything else dispatches without CHARC. The orchestrator **self-certifies** "no tripwire crossed" in the brief; false negatives are caught at phase audit and feed back as a process lesson. **Rationale:** the tripwires are the *mechanism* of the swimlane design — they route exactly the cross-scope judgments a scope-limited role can't make (§4) UP to the role that can. A per-brief gate was rejected as process bloat; the tripwire gate + phase audit is the balance.

## 5.1 THE REVIEW LADDER — what each instrument STRUCTURALLY cannot see (adopted 2026-07-30; every rung demonstrated in one week on Phase 21)

§5 routes *what* gets reviewed. This bounds *what a review can be credited for*. Each rung has a blind spot that is a property of the instrument, not of the reviewer's care — so **no rung may be credited as coverage for the rung below it.**

**THE MERGE-TIME COMPOSITION READ ASKS THE RUNTIME QUESTION, NOT ONLY THE FILE-SET ONE (2026-09-08, the 0038 witness; five seats recited a sequence the code forbids).** Composition is CODE × THE LIVE SCHEMA at the moment of merge, not two arcs' file sets. `connect()` refuses any schema version but the expected one, so a step that opens the live DB is UNRUNNABLE between a schema-bumping merge and its migration — "live run, then migrate" cannot execute the moment the merge lands; the baseline is the LAST PRE-MERGE run and the live verification is post-migration by construction (run 171 was step 0 for 22-A4). The code-level halves live in CLAUDE.md §Gotchas (the pre-image bullet's 09-08 amendment; the exclusive-lock bullet); this paragraph is the gate-level half.

**THE DISCHARGED-DEFERRAL NOTE (adopted 2026-08-07 — orchestrator-found and -generalized, RD-classified, CHARC-canonicalized; gotcha #31's sibling, SAME FAILURE IN BOTH TENSES).** A code comment recording a deferral ("recorded here, NOT fixed here") is a **falsifiable assertion about current code that no test can reach** — it has no assertion surface, so nothing catches its falsification when a later arc discharges the deferral forty lines below it. The instance: a 3a-era note survived 3b's implementation of the exact fix it denied; a director then banked a state-file row FROM that note, and when the next reader did the correct thing — went to the code to verify the row — **the stale comment CORROBORATED the stale row: the cross-check that should have broken the false belief confirmed it.** Two independent-looking artifacts, one common ancestor. It defeats verification-by-cross-check rather than merely surviving it, and it punishes precisely the diligent reader. Three rules:

1. **When an arc discharges a recorded deferral, deleting the deferral note is PART of the fix** — the discharge IS a supersession event, and supersession is performed by replacement (§2's rule, met in code rather than in a plan).
2. **Re-verify EVERY claim the note makes against the symbols it names — INCLUDING the claims you intend to keep.** The keepers are the dangerous ones: they survive the cleanup that was supposed to be the safety net, **and they leave carrying a certification — *this block was reviewed at commit X* — that the deleted parts never get. A partial cleanup is worse than none, because it launders what it leaves behind** (RD's supersession of his own deletion-only formulation: the wrong remedy from the wrong diagnosis — deletion fixes a documentation problem; re-verification fixes an unreachable assertion). **THE DETECTION METHOD IS PART OF THE RULE: a claim that names a symbol is checked against that symbol's CONSUMERS, not against the paragraph it sits in.** Neither director caught the fourth claim by reading the block — it reads plausibly, which is what careful prose is engineered to do; it fell out of `grep -n` on the named symbol and a count of its five consuming sites against the claimed one. The external authority was four lines of grep away — the review-ladder's prose-reads-the-document-against-itself blindness, in miniature.
3. **A doc-vs-code cross-check is only independent if the two did not come from the same source — PROVENANCE, not count.** The discharge also clears any downstream row banked from the note: one defect, two bodies.

**REFINEMENT (2026-08-09, from executing ruling 4): THE CLASS LABEL IS NOT THE DIAGNOSIS — verify FIRST, and let the verification choose between DELETION and CORRECTION.** Rules 1 and 2 can point in OPPOSITE directions, and rule 2 decides which applies: the `build.py` note classed as a discharged deferral was NOT discharged (the hole it flagged still existed; the arc that would discharge it had not executed) — deleting it per rule 1 would have DESTROYED a live and accurate flag; what was false was one claim embedded inside it, at two sites, and the corrected flag is STRONGER than the original. **REACH (2026-08-09, the manifest-sweep saga — counts ran 5→6→7 across three parties, the largest enumeration the OLDEST): when a false claim is found in a note, sweep the CLAIM, not just the note — and a TOKEN GREP BOUNDS THE FAMILY FROM BELOW; ONLY A READ ESTABLISHES THE MANIFEST.** A false invariant propagates by PARAPHRASE (`cap` for `zone_cap`; `stop < pivot < cap` for the full names) — same claim, disjoint tokens — so a pattern encodes the claim's WORDING, not the claim. **LOAD-BEARING COMMENTS (2026-08-09, the fifth instance — the ONLY one no automated rung could find): a falsified comment can STEER BEHAVIOUR rather than merely describe it, and when the behaviour it steers is PRESENTATION, every rung above the operator witness is structurally blind to it.** `app.css:605`'s rationale ("the control rides INSIDE an alarm block, so no box of its own") was falsified by item 4 moving the control out — and the rule went on doing exactly what it prescribed; 13 strong rounds, a disjoint cold audit, 10,516 tests and an RD gate all passed over it, and the entire cost landed on the person reading the screen. **THE THIRD COMPOSITION INSTANCE HAS A PROPERTY THE FIRST TWO LACKED — THE COMPOSED DEFECT IS A DEADLOCK, AND BOTH HALVES ARE STILL CORRECT (2026-08-12, VSTS, found at an operator witness on step one before anything was clicked).** Two individually-correct decisions: (1) 21-G/21-B soundness — withhold the prepared order when the price regime is undeterminable, never assert a regime from a close the card refuses to date; (2) 3a's ledger design — a decline is a decision about the framework's OWN order, so the ledger requires that order on the row. **Composed: a mandate that stays off-screen long enough to lose its price regime becomes PERMANENTLY UNDECLINABLE — the staleness that makes it need clearing is exactly what makes it unclearable.** And the SAME undeterminable-regime condition silences the missing-order alarm (deliberately — *"an absent price is not evidence of a wrong mismatch"*), so the framework showed a mandate ARMED with an 18-session horizon for NINE DAYS after the operator had cancelled its order at the broker (2026-08-03). **Three silences from one root condition: no prepared order, no decline control, no alarm — the framework cannot tell that the order is gone for precisely the reason it cannot let the operator say so.** The instance is inert (no order, no position, no exposure — a ledger divergence only); the CLASS is not, because the next mandate killed at the broker with no way to tell the framework may not be. **What distinguishes this from instances 1 and 2: those were CONTRADICTIONS (one file carrying both rules; two incompatible doctrines), fixable by making the artifacts agree. Disposition (operator to ratify): the instance expires on its own horizon 2026-09-08; the class routes to Phase-22 — a path that records ABANDONMENT without requiring the order the framework never offered (the orchestrator's option d), which is also RD's mirror-asymmetry case made concrete: `untracked_broker_position` catches broker-has-what-the-journal-lacks, and this is framework-holds-what-the-broker-no-longer-backs, reaching the operator as silence rather than as a discrepancy.

**AN ACCEPTANCE GATE NEEDS A PER-CLAUSE DISCRIMINATOR (2026-08-24, the 22-A tri-case gate — orchestrator-found, RD-confirmed against his own gate): for EACH clause of the bound being encoded, the gate must contain a case that FAILS the null implementation of that clause.** RD's tri-case acceptance test was fully specified by live data and looked binding — and an implementation that omitted the invalidation comparison ENTIRELY passed all of it, because no live case could reach the check (AMN, the intended negative control, has zero latch rows — the instrument post-dates its entry — so it passes trivially through the no-latch fallback). **A gate built only from live cases inherits the ledger's coverage, and the ledger holds only the states that have happened.** When no live case exercises a clause, the discriminator is a LABELLED SYNTHETIC in the real row shape with ONE mutated value (the 18-B.1 raw-insert technique — legitimate because it tests DETECTION of a state the ledger does not hold), pinned tight (RD: use the real incident's breach GEOMETRY — five cents, not a gross breach a sloppy encoding still catches) and paired with its BOUNDARY twin (equality → the opposite outcome), so the inequality direction is pinned rather than guessed. This is the fixture-routes-around-the-branch class at the ACCEPTANCE-TEST level — one instrument up from where it was first caught, consistent with every class in this file climbing one level after being named. **The companion failure shape, RD's own diagnosis of how it happened: BANKED-BUT-NOT-PROPAGATED — he held the disqualifying fact (proved for Demand A's tier-2 ruling: the latch instrument post-dates AMN) and banked its FIRST consequence without applying its second to a claim of his own, hours apart.** A banked fact is not a propagated one; when a fact is banked, ask what ELSE it disqualifies.

**A WORKTREE IS DELETABLE ONLY WHEN ITS PLAN IS ON `main` *AND* ITS GITIGNORED REVIEW EVIDENCE IS PRESERVED OUTSIDE THE REPO (2026-09-06, CHARC; the 22-A3 merge surfaced the gap).** The plan-on-main rule (adopted at the Demand-C cleanup near-miss) covers the SPEC. It says nothing about the EVIDENCE — the `.copowers-findings.md` ledger, every `.codex-review-r*` transcript INCLUDING the void/disqualified rounds (the round-validity discipline's own proof of work), the reviewer-B transcripts and prompts — all gitignored, all existing only in the worktree, none recoverable once it is torn down. **Live instance: `22-a-plan` held TWELVE such artifacts (11 MB, ten rounds of the 22-A planning loop) preserved NOWHERE, and no step in the teardown ritual would have flagged it** — the ritual checks that a plan is on `main`, not that a phase's review evidence is out. Caught only because the orchestrator swept every worktree for artifacts existing only there, and caught on the SECOND count, after an `ls` without `-a` had produced the wrong number (dotfile blindness — the same slip it had caught in itself hours earlier). **The convention, now binding rather than proposed — AMENDED 2026-09-07 to COPY-PER-ROUND (replacing copy-at-teardown):** every review artifact — each `.codex-review-r<N>.txt` and its `.codex-prompt-r<N>.md`, the `.copowers-findings.md` ledger, every reviewer-B transcript and prompt — is copied to `~/swing-data/review-transcripts/<arc-or-worktree-name>/` **the moment that round's five assertions pass, by the loop itself**, so the durable location is never more than one round behind; the teardown check becomes a RECONCILIATION (a dotfile-aware `ls -a` of the worktree root against the destination) rather than the first copy. **AMENDED AGAIN THE SAME DAY (coa-chess EVIDENCE_PER_ROUND, adopted): the cumulative LEDGER is COMMITTED into the worktree per round** (`<plan>.ledger.md` beside the plan), so an accept cites a path on `main` and the evidence merges with the spec; only the multi-megabyte transcripts live outside the repo, named in the ledger by path and size. coa-chess's version of our gap was a step further back — its ledger lived ONLY in cell and dispatcher transcripts under 30-day default retention, so its accept records were citing evidence that would have aged out in a month. **Why the 2026-09-06 form was insufficient, found one day later on 22-A4:** the review loop copies each round's transcript to the SESSION SCRATCHPAD (`AppData/Local/Temp/claude/<project>/<session>/scratchpad/loop/`) and REMOVES it from the worktree between rounds, restoring the full set only at report time — so for the whole of an eight-round arc the canonical copy of its evidence sat SINGLE-COPY in a session-scoped temp directory, and a rule that fires at teardown could not have seen it. Nothing was lost; the exposure was real and uncovered by the rule written to cover it. **Two corollaries from the same day:** (a) between rounds the worktree root is NOT where the evidence is — a director checking the gate mid-round reads the durable location, not the worktree; (b) a `find -maxdepth N` that reports an absence is a bounded search reporting a fact — the orchestrator's own search could not have reached the scratchpad at any location and returned "no copies" as a ruled-out location (self-caught, self-corrected). The recipe line naming the `cp` in the loop script is the orchestrator's to mirror; this paragraph is the rule. **Why both halves are needed:** the spec says what was BUILT; the evidence says what was CHECKED and what was REJECTED — a phase whose disqualified rounds are lost can no longer prove its assertions were ever enforced.

**THE PER-ROUND EVIDENCE SET NAMES THE DIFF INPUT (2026-09-09, the 22-A4 teardown).** The teardown hash reconciliation of both worktree roots found the two `.codex-diff*` files — the INPUT each review round actually read — preserved NOWHERE: the copy-per-round rule listed prompt, transcript and ledger and not the artifact those three are about. Recovered at teardown by the reconciliation the rule mandates, which is the rule working one step late. The set is FOUR: **prompt + diff input + transcript + ledger**, copied together per round. A transcript over an unpreserved diff proves that a review happened, not what it reviewed.

**A SEAT-RELATIVE LADDER MAKES "THE REFUSAL REASON" A PROPERTY OF (WORLD, SEAT) — NOT OF THE WORLD, SO ANY SPEC PINNING A REASON MUST NAME THE SEAT (2026-09-01, the 22-A `4c-i` third thing).** Determined by execution after both candidate causes were refuted: an authorization ladder run from the SUBJECT's seat admitted, and run from the RIVAL's seat refused `ambiguous_ticker_orders` — **each classification correct in its own direction.** The specified verdict was unreachable not because a rung misclassified but because **an earlier rung fires first from the other seat**, which makes the second leg structurally unreachable for *any* two-order fixture with one live and one dead. **The defect underneath was legibility, and it was the plan's own principle:** an order whose own mandate is dead was refused with a competitor-CARDINALITY complaint when the actionable truth was *"this mandate is dead, superseded"* — and the spec itself says *a guard that says only "ambiguous" cannot be acted on.* **Rung ordering had made the LESS actionable reason win.** The fix shape that generalizes: **where two refusals are both true, prefer the MORE SPECIFIC one — a refusal-legibility enrichment, never a reordering** (the rung still runs first and still refuses; only the reason is chosen), which cannot convert a refusal into an admission and is therefore safe under the governing asymmetry. **And the selection must inherit the three-valued discipline of whatever it consults**: proven-dead selects the specific reason; proven-live OR UNPROVABLE falls through to the general one — a two-valued check here reintroduces exactly the unprovable-read-as-absent inversion the population rule was corrected for.

**WHEN A SPECIFIED VERDICT PROVES UNREACHABLE, THE FIRST QUESTION IS WHETHER THE PRE-EMPTING STEP IS CORRECT — NEVER WHETHER TO MOVE THE ASSERTION (2026-09-01, the 22-A `4c-i` UNVERIFIABLE; CHARC-ruled).** A test specified an outcome that a rung running earlier pre-empted, and the honest resolution taken was to assert at the lower grain and DECLARE the divergence. **Read at both sites, the specification did not contradict itself:** the case's own text says the dead order *"is not a competitor under the population rule,"* and that rule's table lists horizon-expired explicitly under **not a competitor**. Both halves agree — so a pre-empting verdict means the CODE disagrees with both, and the unreachability is a candidate PRODUCTION DEFECT rather than a spec quirk. **Moving the assertion down a grain would have converted a possible defect into a documented divergence**, and the honesty of the declaration is exactly what makes that dangerous: **a declared divergence reads as settled.** This is the sharpest form of the class this arc kept meeting — an instrument's own disclosure making a defect look adjudicated. **The ordered procedure: (1) re-read BOTH specification sites, because "the plan contradicts itself" is a conclusion, not an observation; (2) if they agree, determine BY EXECUTION whether the implementation or the fixture is wrong; (3) a grain change is the LAST resort and returns to the ruling authority, never a local resolution.** Corollary for graders: an UNVERIFIABLE verdict is doing its job when it SURFACES rather than absorbs — it is a routing signal, not a disposition.

**A RULED MECHANISM CARRIES ITS ADMISSIBILITY PRECONDITIONS, OR IT SHIPS THE MECHANISM'S FAILURE MODES AS DOCTRINE (2026-09-02, three instances in one week across both directors; CHARC's own is the sharpest).** CHARC ruled *"if `commit()` raises, RESOLVE BY READ — never report indeterminate when a read can settle it"* as the R9-03 contract. Implemented faithfully, it CLOSED one single-fault defect and OPENED four — two of them FALSE-SUCCESS paths on the money-bearing entry path, telling the operator *"Do NOT retry — the entry exists"* about a write that vanishes at connection close. **The ruling took "a read can settle it" as a primitive. It is not.** It decomposes into two preconditions the ruling never stated: **VISIBILITY** (the read must observe DURABLE state — a read on the writer's own connection inside an unresolved transaction is the writer quoting itself) and **IDENTITY** (the read must identify OUR attempt — a rolled-back rowid is reusable, so `WHERE id = ?` can confirm a concurrent writer's row). The second precondition **does not exist in the schema**, so clause 2 was not implementable as ruled, and the residuals pointed into the one direction nothing belts — the untracked-position direction. RD's endorsement inherited the same gap (*"I took 'present' as a primitive"*), and his P1 ruling the same week was recorded without its REASON. **Three instances, one shape: a ruling states WHAT with confidence and omits the CONDITIONS under which WHAT is admissible.** The rule: **a ruling that prescribes a mechanism states the preconditions that make its evidence admissible, and names which of them exist TODAY** — a precondition that does not yet exist converts the mechanism into a follow-on with a primitive to build first, not a clause to implement now. **Fourth instance, same day, same author (2026-09-02, S9 step 5):** CHARC specified a before/after byte-diff witness — same dry-run against the v36 backup and against live v37 — without the precondition that the code can OPEN both schemas; post-merge code refuses v36 by design, so the pairing was a combination that never existed. The corrected witness varies code and schema TOGETHER, and gains the control the original lacked: **the two sides must be PROVEN to run different code, or a before/after diff is vacuous by construction** (the editable-install gotcha resolves MAIN from any worktree — an unproven "pre-merge side" silently runs post-merge code and the diff is trivially identical). A witness that cannot fail is the 33/36 class at the operator gate. **Corollary, RD's, and it is alarm-never-assert at the transaction boundary:** a function may RAISE the alarm (indeterminate) but may never ASSERT durability from evidence that cannot identify the attempt. Re-raise never claims a row exists.

**THE ENTRY-vs-LABEL TEST FOR ANY COHORT-PROVENANCE GUARD — CLAIMED vs ABSENT decides the jurisdiction of "NEVER" (RD-ruled 2026-09-02 on B's P1; CHARC-canonicalized as the operational form of the cohort-bookkeeping-never-blocks-a-money-bearing-entry principle).** Reviewer B's post-fix pass found a production refusal — an order-bearing request carrying a `pattern_evaluation_id` anchor that the server-derived world REFUTES is refused with HTTP 400 — and asked whether it violated the principle. **It does not, and the discriminator generalizes past this case: "NEVER" governs refusals grounded in the framework's inability to PROVE provenance the request never CLAIMED, where the honest-unset row exists and IS the honest answer. A CONTRADICTED EXPLICIT CLAIM has no honest row:** NULL silently overrules the request's own assertion (curation by machinery), and non-NULL records a REFUTED citation into an evidence chain (minting evidence). **The operational test, to be applied at every guard's site declaration so no future guard needs a ruling:** *"Could this row be written honestly with the disputed keys NULL plus a named warning?"* **YES → the guard refuses the LABEL** (honest-unset passes, entry proceeds). **NO, because NULL would silently discard an explicit claim the request carries → the guard refuses the ENTRY, and its message MUST name the recovery.** RD's framing correction is load-bearing and travels with the test: **this is not "a live exception to the principle" — an exception invites more exceptions; a stated discriminator keeps NEVER meaning never inside its jurisdiction.** The round-trip that produced it was the cost of a leg-6 ruling recorded WITHOUT its reason — the accepted-limitations rule's own prediction, banked by RD against himself: *a disposition without its reason gets re-litigated forever.*

**AUTHORIZE-THEN-ABORT: A GUARD THAT CAN REFUSE A SERVICE-AUTHORIZED WRITE MUST BE PRECEDED BY A SERVICE CHECK THAT REFUSES THE SAME INPUT WITH A TYPED MESSAGE (2026-09-01, orchestrator-routed, FIVE instances in one arc; CHARC-ruled).** The shape: the service ADMITS an operation, and a downstream SQL trigger or CHECK then ABORTS the write — so the operator receives a raw `sqlite3` error where the service would have given a legible refusal. Measured instances include a three-valued input collapsed to two so *unknown* read as PASS while the trigger required TEXT (`R6-05`); the service STRIPPING a key the trigger binds by `json_extract`, aborting with the generic citation-graph message (`SS-4`, *"an authorize-then-abort delivering an ILLEGIBLE refusal"*); and `+inf` passing a `> 0` CHECK, being authorized, then failing `json_valid()` at the citation INSERT (`R15-02`). **The architectural rule: THE TRIGGER'S PREDICATE SET MUST BE A SUBSET OF THE SERVICE'S ADMISSION PREDICATES.** The trigger is a BACKSTOP against writes that bypass the service — never the discovery point for an input the service admits. **Its enforcement is a closure check, not a roster** (the shape already proven at `AL-3`/`SS-12`): every trigger refusal predicate maps to a named service-side check, asserted mechanically in both directions so a predicate added to either side without its twin fails loudly. **Its test shape is a satisfiability proof in the negative direction:** for each trigger refusal reason, prove the SERVICE refuses that input first with a typed error — i.e. that the trigger's refusal is UNREACHABLE through the service. **This is the persist-canonical family's other half:** that rule governs where SQL re-derives a judgment the service owns; this one governs where SQL holds a STRICTER predicate than the service checks. Both are the service and the schema disagreeing about the same input, and both resolve by making the service the single authority that speaks to the operator.

**A COVERAGE METER THAT BINDS A CASE ID TO A TEST *NAME* MEASURES NOMENCLATURE, NOT COVERAGE (2026-09-01, the 22-A "146 of 146" correction; RD stated the class, CHARC canonicalized).** The arc reported 146/146 cases traced to passing node ids for weeks — and the binding was the test's NAME. Demonstrated: the plan's S3.4 specifies case 4 as *place-intent WITHOUT a validity row → falls through*; the test named for case 4 builds a broker-ACCEPTED order and asserts ADMISSION — **the opposite of its specification, counted as covered.** **This is the existence half of existence-vs-completeness, met now at a coverage meter** — after counts, greps, and absences. The consequences are two: **a number built on name-binding must not be restated until every binding is re-audited SEMANTICALLY** (does the test assert what the spec states), with that method reported; and **a director's clearance that read SPECIFICATIONS never covered their IMPLEMENTATIONS** — RD narrowed his own 22-A gate on exactly this ground, and the narrowing is the correct form: *a gate covers what it read.* The case that mattered most was the one control separating keying on ANY latch row from keying on a broker-VALIDATED order — the evidence standard a whole doctrine ruling turned on, left unverified by a test asserting its inverse.

**THE B GATE'S ABSENCE IS NOW BLOCKING AT THE DIRECTOR GATE, NOT ONLY AT THE ORCHESTRATOR'S DILIGENCE (CHARC, 2026-09-01).** Charter §2.9 makes reviewer B a REQUIRED gate on production-code arcs, and on 22-A **fifteen rounds of A ran before B ran once** — the largest process gap in the arc, found and named by the outgoing orchestrator itself, whose single B pass then returned `NEW_CRITICAL_MAJOR_FOUND` and produced the 146/146 correction. A mandatory gate that a knowledgeable party can simply not reach for fifteen rounds is the D28 shape, and the answer to D28 is a mechanical guard rather than a firmer promise. **So: CHARC's merge gate now REQUIRES the B transcript — its path, its five mechanical assertions, and its verdict — named in the merge request. No transcript, no clearance.** **And the gate reads for PURPOSE, not letter (clarified 2026-09-01 on the orchestrator's own question): B must have run on THE TREE BEING MERGED.** A transcript auditing an earlier tree satisfies the words and proves nothing about the artifact in front of the gate — the same stale-instrument shape as the temporal clause. **B is NOT required to return clean** — that would be the unreachable gate the introduced-vs-banked rule exists to prevent; what is required is that every finding be DISPOSITIONED under that rule. A `NEW_CRITICAL_MAJOR_FOUND` verdict whose findings are all banked-with-evidence clears; a clean verdict on a stale tree does not. A check nobody gates on is not a check; this one is now gated by the role that can refuse the merge.

**THE REACHABILITY CLAIM LIVES IN A TEST (2026-08-11, quoted verbatim from the test file that recorded its own two failures in opposite directions — first claiming a constructor guarantee, then claiming unreachability, both falsified silently):** *"A comment asserting REACHABILITY is a claim about the whole surrounding control flow, and the next change to that flow falsifies it silently — so the reachability claim now lives in a TEST."* The note that recorded its own failures was deliberately LEFT by the sweep — a note documenting the class is not an instance of it, and deleting it to make a grep clean would be the sweep eating its own evidence. Companion evidence for the reach rule, from the same sweep: THREE independent patterns each missed a site the others caught (union 10 candidates; only reading separated 3 real sites from 7 lookalikes) — the rule demonstrating itself on a live sweep rather than being asserted.

**A VERIFICATION TOOL IS AN ARTIFACT (2026-08-11, two instances in one day, both the orchestrator's own, both self-caught): "my checker says so" is a claim that needs the same sourcing as "my grep says so."** Instance one: a content-equality guard written before a destructive step, NOT GATED ON (it printed DIFFERS and the delete ran anyway — safe by luck), and itself WRONG (LF compared against CRLF, so it cried DIFFERS on identical content — the cry-wolf family one layer down). Instance two: an AST comment-only checker reporting a difference on a diff containing nothing but prose — resolved by reading every changed line and saying so in the commit message rather than claiming a proof that did not exist. The two rules: **a check you do not gate on is not a check** (RD's keeper), and the direct reading is often both cheaper and stronger than the instrument built to avoid it.

**A COROLLARY WORTH ITS OWN LINE — A SEAM COMMENT PROMISING FUTURE INHERITANCE IS UNENFORCEABLE BY CONSTRUCTION.** The site carried: *"THE 21-A SEAM, NEVER RE-IMPLEMENTED. Whatever 21-G does to make the close sound flows through automatically."* That is a claim about an arc that had not happened yet, so **no test could pin it** — and the test they did write pinned the wrong half (that the module contains no independent comparison, i.e. what the code does NOT do, rather than what the caller MUST do). **The comment still reads TRUE after being silently voided, which is exactly the invisibility property that makes preserve-the-quote its own row above:** the record degrades with no signal. A comment may describe what the code does today; it may not promise what a future arc's change will do to it.

**`NO_NEW_CRITICAL_MAJOR` IS THE END (operator-ruled 2026-08-11; REFINED same day by the operator and re-canonicalized by replacement).** The A-loop terminates at the FIRST clean verdict. **Post-convergence MINORS may be corrected WITHOUT an additional round — correcting a minor does not meet the threshold for re-attaching convergence; the FULL FAST SUITE on the final head is the verification that covers minor-scope corrections.** The verdict and the green suite JOINTLY describe the shipping tree. The fork this closes was real: under the unrefined tree-attachment reading, fixing a post-verdict minor re-attached the convergence obligation, bought another round, and sustained a loop in which every individual round looked diligent (D31-exit R18–21: four clean verdicts, four true minors, one operator-facing sentence). **What re-opens the loop is the SCOPE OF THE CHANGE, not its timing: only a post-verdict change of critical/major scope — one that alters behaviour the verdict examined — invalidates the verdict and requires a further round.** Minor-scope corrections (wording, comments, prose, cosmetic fixes) are fixed, suite-verified, and REPORTED in the return; A's clean verdict is the implementer's exit condition and drives its completion report. **The composition that makes this safe NOW: the reassigned B runs at the orchestrator's gate over the finished tree** — the net for anything a post-convergence correction could hide is an independent pass by different hands, which did not exist as an instrument when the 3b fix-and-re-run precedent was set. The loop's owner does not adjudicate its own tail, and the tail no longer costs a review cycle per sentence.

**WHO HOLDS THE SECOND EYE (operator-ruled 2026-08-11, CHARC-canonicalized): the ORCHESTRATOR runs the B review (`codex-auto-review`); the implementer runs A.** A is iterative and needs the author's hands; **B is a single pass over a finished tree, and its entire value is being a DIFFERENT perspective — which is eroded when the author chooses its PROMPT, its INPUT SET, and the ADJUDICATION of its findings.** Three levers over an ostensibly independent check, and the compensating transcript-read does not cover the gap: it catches a fabricated verdict, not a prompt quietly narrowed until the reviewer stops finding things — the narrowed prompt IS the transcript. The two live erosions that grounded the ruling were both SELF-REPORTED (the content-filter rephrase; the scratch-in-input echo) — not misconduct, but detectable only because the implementer chose to report them, which is the asymmetry the ruling removes. **Structural gain: B now runs at the gate that actually blocks the merge — the reviewer and the merge-blocker become the same hands.** **The natural experiment (run ONCE, at the transition, by design): on the same finished tree, the author's B found 6-and-converged-clean while the orchestrator's B returned `NEW_CRITICAL_MAJOR_FOUND` — including a regression INTRODUCED by the arc and BLESSED BY ITS OWN TEST** (identity asserted from a date alone on a fixture carrying no identity — the fixture-routes-around-the-branch class in its assertive form, worse than the catalog entry because it documents the regression as the intended contract). One instance, not generalized — but it is the instance the ruling predicted, and it arrived immediately.

**THE B GATE'S STOPPING CONDITION (orchestrator-proposed 2026-08-12, adopted by RD as the concession his own boundary required, CHARC-canonicalized): B IS CLEAN FOR MERGE WHEN IT RETURNS NO UNBANKED CRITICAL OR MAJOR THAT THIS ARC INTRODUCED.** Pre-existing findings are **BANKED** — named, with file:line, mechanism, and reachability evidence — never fixed. **The contradiction it resolves:** B is a whole-artifact reviewer BY DESIGN (that is the delta-blindness cure), so pointed at a file carrying real debt it returns real findings indefinitely — four consecutive rounds at 3/2/3/3 majors, the last being one introduced defect and two pre-existing template defects in a file whose entire diff was 7 insertions / 2 deletions. **"Merge when B returns clean" is therefore UNREACHABLE on any such file**, and held literally it forces one of two failures: the arc never merges, or it absorbs the surrounding surface — the unbounded-arc failure the INTRODUCED-vs-PRE-EXISTING boundary exists to prevent. The gate adds no principle; it states **which side of the already-ruled boundary the GATE reads.**

**DEFAULT TO INTRODUCED — BINDING.** The burden of proof sits on whoever claims PRE-EXISTING, and absence of evidence resolves toward the arc's own account, because **the cheap failure is fixing something you did not break; the expensive one is shipping something you did.** The evidential standard, stated so it cannot decay into an assertion: a `git log -S` on the changed symbol, or a `git diff --stat` proving the region untouched, **QUOTED in the adjudication** — never "this looks pre-existing." **CONTESTED PROVENANCE = INTRODUCED** (RD's clarification, already ruled twice in practice): where a symbol predates the arc but the arc changed its meaning or made it reachable, the defect is the arc's — **provenance is about the DEFECT, not the LINE.** The banking obligation is not decoration: **a gate reading INTRODUCED without it would be strictly worse than the unreachable one**, because that is the route by which "pre-existing" becomes "forgotten."

**THE UNIFYING OBSERVATION (CHARC, on canonicalizing the second one): the harness has now hit the NO-STOPPING-CONDITION class at BOTH reviewers, and both resolved the same way — by scoping the gate to what the arc OWNS rather than to what the reviewer can FIND.** A's version (the termination ruling): the **SCOPE of a post-verdict change** decides re-opening — minor-scope corrections are verified by the suite, not by another round. B's version (this gate): the **PROVENANCE of a finding** decides blocking — pre-existing findings are banked, not fixed. **Both loops were unbounded for one reason: their stopping conditions were stated over the REVIEWER'S OUTPUT rather than over the ARC'S RESPONSIBILITY.** Expect the same shape wherever a review instrument is pointed at a surface larger than the arc that summoned it — and reach for the same fix.

**THE ACCEPTED-LIMITATIONS DECLARATION (2026-08-12, three data points): a standing review instrument measured against a contract that OMITS what has already been ACCEPTED re-finds the accepted items EVERY ROUND, FOREVER.** That is not the reviewer malfunctioning — it is an INCOMPLETE CONTRACT, and it is the mechanism by which a second eye degrades into a treadmill. (Distinct from the schema-prevented treadmill, where the findings are not real; **here every finding is real and every one is already decided.**) **The countermeasure: declare the accepted decisions in the review prompt WITH THEIR REASONS, and EXPLICITLY INVITE THE REVIEWER TO CHALLENGE THE REASONS.** Evidence: round 2 raised a deliberate contract that nothing declared; round 3 declared it with its live-evidence reason and it was not re-raised — while B still returned three majors; round 4 carried all five limitations at full length — none re-raised, three majors still returned. **RD's caution is the load-bearing half, and he attached it against his own rulings: each entry carries its REASON, not just its disposition** — *"every entry on it is a decision I can be wrong about — I have been twice this week, and both times the correction came from a B round reading something I had declared settled."* Proven the same round: the one entry the reviewer engaged, it engaged **on the merits**, and found the acceptance unsound. **The invitation to challenge is what makes it a contract rather than a gag, and it is not optional.**

**A CELL'S CONTEXT DEPTH IS A DISPATCHER-READ FIGURE, CHECKED AS A PRECONDITION -- A CELL CANNOT SEE ITS OWN (2026-09-07, coa-chess CHARC's finding, reproduced here and adopted; the instrument is `scripts/cell_depth.py`).** A dispatched implementer cell never receives a user prompt, so no `UserPromptSubmit` hook ever fires for it, and it has no view of its own `usage`; a rule that asks a cell to report or bound its depth rests on a number the cell structurally cannot read (coa-chess wrote exactly that rule, and two dispatches went to cells at ~540K and ~650K before the operator caught them). The dispatcher CAN read it: every assistant record in `~/.claude/projects/<slug>/<session>/subagents/agent-a*.jsonl` carries `message.usage`, and `input + cache_read + cache_creation` on a record is the context presented that turn -- the last record is the current depth, the maximum the high-water mark. **Measured on this project the day the rule landed: 37 cells on disk, 24 peaked above 400K, 3 above 800K; the 22-A fix leg ran to 990,589 over 1,019 turns, and the 22-A4 planning cell was at 752K mid-loop while nobody could see it.** Why it matters: every turn re-reads the whole context at the cache-read rate, so a round at 800K costs ~2x the same round at 400K -- depth multiplies round count, and depth was the invisible factor. **The rule, in three clauses:** (1) the ORCHESTRATOR runs `python scripts/cell_depth.py --live <h>` BEFORE assigning further work to a live cell and at EVERY review-round gate, and fills the round ledger's depth column itself -- a cell's self-estimate is not a record; (2) the check is a PRECONDITION, never a caveat attached to an assignment (both coa-chess mis-dispatches were the right check in the wrong order); (3) a cell past the cap (400K, the calibrated default) is RE-DISPATCHED from a fresh context off the committed plan + the preserved per-round ledger -- the same shape as a director rolling a generation, and cheap for the same reason (the state is on disk). Corollary for any spend arithmetic: **a sum over a project's transcripts MUST descend into `subagents/`** -- a project-level glob misses every cell (coa-chess undercounted an arc by 43%). The `[ctx]`-style self-report remains valid for DIRECTORS only, where the hook fires.

**DESIGN IS SETTLED BEFORE THE PLAN LOOP OPENS, AND DIRECTORS RULE IN ONE PACKET — a review loop is not a design forum (operator-concurred 2026-09-07; CHARC-authored on the evidence of 22-A, Demand C and 22-A4).** The plan loop is a PROSE-COHERENCE instrument (the ladder's first rung): it reads the document against ITSELF and has no access to the authority a design question is decided by. Used as the arena for design it produces the 22-A4 shape — forks discovered at round 1, routed at round 5, ruled across rounds 6–10 by two directors over mail, each ruling followed by an amendment and a ~400K-token round reviewing its own wake, on a plan that grew 2,025→2,696 lines while it was being reviewed: 3.80M tokens on a plan stage for ~200 lines of code. **The rule, cross-role:** (1) a writing-plans dispatch opens with a **premise + fork census** (no Codex) that routes every fork and needed ruling as ONE packet, both branches of each fork specified; (2) the directors rule the packet in ONE pass each — a ruling that arrives as a stream of separate messages is a stream of rounds; (3) **no review round runs while any ruling is outstanding**, and a fork discovered mid-loop STOPS the loop and re-enters at (1); (4) the plan itself is a task ladder + test roster capped at ~1,000 lines, its argument and history in the ledger and the brief; (5) plan loops run at most three counted rounds at the `fast` tier, then a self-sweep, then execution — because **only execution finds an unimplementable spec**, and the suite finds a plan defect in seconds at zero review cost. The implementer-facing form is the recipe's PLAN-STAGE PROTOCOL; this paragraph binds the directors' half — a director who answers a routing packet piecemeal has re-opened the loop. **CHARC's own account of one input:** the canon in this section accretes — every round's findings become rules, and the next reviewer reviews against a larger canon and finds more. Custodianship of that weight is mine; the phase-close compaction of §5.1 is now a standing item, not a hygiene nicety.

**THE BASE CARRIES THE RULES (adopted 2026-09-07; coa-chess `0b38be39`).** A brief that says "follow the recipe" is only as good as the recipe IN THAT WORKTREE: a rule landing on `main` does not reach a branch based below it, and the cell reads its own tree. Live instance here the day it landed: `.worktrees/22-a4-plan` is based on `edfea928`, and every rule of 2026-09-07 (the plan-stage protocol, dispatcher-read depth, per-round evidence, the intake check) sits above it — a cell in that tree reading "the recipe" reads the day-before recipe. Pre-dispatch, the orchestrator names the rules the brief depends on, verifies each in the branch's OWN copy of the recipe + the docs it cites, and records the base SHA checked; a stale base is rebased BEFORE dispatch, never patched by a brief clause. The orchestrator's checklist carries the step; this paragraph is the rule.

**THE COMPOSED FORM — THE INVARIANT IS "THE CELL READS CURRENT RULES," NOT "THE WORKTREE CONTAINS THEM" (2026-09-07, CHARC; the orchestrator's no-mid-ladder-rebase mechanism collided with the rule above the day it landed).** Both goals are sound — a published SHA moves exactly once; a cell reads the rules that bind it — and held literally they cannot both be satisfied on a ladder whose rules move mid-arc, which is every ladder. Rebase is ONE way to satisfy the invariant and the right one at cut time. MID-LADDER the equivalent is the orchestrator's own mechanism applied to the rule docs: the dispatch names the recipe and this document by MAIN-REPO ABSOLUTE PATH and records the `main` SHA they were read at ("rules read from main @ <sha>", never "worktree at <sha>"). The prohibition that stays is the one that mattered: a brief CLAUSE paraphrasing a rule is the failure; a POINTER to main's copy is not a paraphrase. The worktree's own recipe is then stale BY DESIGN and the brief says so in one line, or the cell — which the recipe tells to read its own tree — reads the wrong one and is right to. The five implementer cell definitions (`.claude/agents/implementer-*.md`) carry the absolute path and the warning as of 2026-09-09.

**ITS SIBLING: A HANDOFF CARRIES POINTERS TO DEFINITIONS, NEVER PARAPHRASES (2026-09-08, the orchestrator's own diagnosis of its false "REVIEWER B COMPLETE").** A predecessor handoff wrote "reviewer B (your own second eye)"; the successor read "your own" as licence and reported a hand review — composition read, one mutant, one finding — as B, and the arc as merge-ready, when charter §2.9 defines B as the codex-auto-review pass and this section's gate requires its transcript on the tree being merged. Neither generation lacked care: **a NAME survives a handoff intact while the DEFINITION stays behind in the charter, and ordinary-speech meaning fills the gap.** A handoff names a term of art WITH a pointer to the text that governs it (charter §2.9; "THE B GATE" here), and a successor fills no term from memory.

**The load-bearing consequences:**

- **Only execution finds an unimplementable spec or an unreachable feature.** A clause its own schema forbids is not a specification, it is a defect in the plan — and no amount of reading finds it, because reading is what produced it.
- **The witness is the load-bearing gate, not the ceremonial one.** Twice in one week it was the only rung that could have caught the defect (RD's phrasing, on his own instrument). A witness script written to a stale brief inherits every blind spot above it, so **when affordances change late, the script is rewritten, not re-run** — and it must drive the ZERO-DATA state too, since a flattering null is invisible to every rung that does not look at a screen.
- **A defect found at one rung generalises to a question for the whole manifest.** The cancel control was found only because someone asked *"what else was in the manifest and is missing in the same way?"* — the right response to a defect is that question, not a patch to the instance.

## 6. Director current-state pointer (cold-start findability)

Each director keeps a single **`docs/<role>-state.md`** (e.g. `charc-state.md`, `rd-state.md`) — the **current-state pointer**, **OVERWRITTEN each session, never appended**. The director **bootstrap reads it FIRST** (deterministic, cheap), then the role charter for stable role/rules context.

The director context-doc **session log is APPEND-ONLY dated history** and must NOT carry "current state / read me first" blocks — current state lives ONLY in `<role>-state.md`.

**Rationale (origin 2026-06-16, a CHARC cold-start):** when the current-state snapshot is appended into the append-only log like history, successive context-exhaustion handoffs accrete duplicate "read me first" snapshots with no deterministic "latest" → the next instance hunts. Separating the mutable pointer (overwrite) from the immutable log (append) makes current state a single cheap deterministic read. This is harness ARCHITECTURE (§2) — it applies to ALL director roles and is baked into the harness-template scaffold (a generic `<role>-state.md`).

**THE ROLLOVER SEQUENCE — a generation tears itself down and launches its own successor (adopted 2026-09-07, operator-directed; coa-chess `298122e8`). Four acts, in this order, NOTHING between them; the order is the entire design and each inversion is a named failure.** The trigger is the depth read, not the window: a director rolls at **~400K context** (token-efficiency item 6a — the previous CHARC ran to 94% of a 1M window because a roll was a human closing a pane), or at a clean boundary the operator names. **The seat reads its OWN number: `python scripts/cell_depth.py --sessions --live 1`** — a main session's transcript (`<slug>/<session-id>.jsonl`) carries the same `usage` records as a cell's, so the same sum is the session's depth (the outgoing orchestrator measured 396,223 this way and rolled on it, first live execution, 2026-09-07). The harness's context line is a thing the OPERATOR reads; with the self-read the trigger is self-serving — the seat that must act is the seat that measures. The gauge's first self-read on CHARC returned 437,783 the minute it landed.

**PRECONDITION — NO DISPATCHED CELL IN FLIGHT (added 2026-09-07, three hours after the rule, from the orchestrator's first attempt; operator-stopped at act 4).** A subagent is IN-PROCESS to the session that spawned it: it dies with that session exactly as the inbox Monitor does, and an executing cell early in a TDD ladder has committed NOTHING (commits arrive per red/green cycle). Measured at the moment the orchestrator was stopped: the 22-A4 executing cell was alive at 243,626 tokens across 123 turns with zero commits in its worktree — act 4 would have destroyed it, not orphaned it, and the handoff's "the cell returns to you" would have been a return to nobody. **The rule:** on hitting the number with a cell running, the seat HOLDS — stops dispatching new work, awaits the return, QAs it, commits, THEN rolls. If context genuinely cannot survive the wait, stop the cell deliberately and preserve its worktree state (a WIP commit on its branch) FIRST; never roll and hope. The check is the same command as the dispatch precondition: `python scripts/cell_depth.py --live 2` — any listed cell whose transcript is still being written is in flight. **And the MIRROR (the orchestrator's corollary from the other side, folded in the same day): do NOT DISPATCH once you are at or past the trigger.** It dispatched executing at ~396K and stood 4K from a rollover that would have destroyed the cell; holding to await a cell you should not have started is the same trap reversed. Read your own depth BEFORE a dispatch as well as before a roll: past ~350K, a dispatch whose return you cannot QA within the remaining budget is a dispatch for your successor to make. **The general lesson (the orchestrator's, against itself, and worth its own line): a trigger a session can serve ITSELF fires more reliably than one a human reads, so its preconditions must be complete BEFORE it is automated** — the `--sessions` self-read made the trigger better and walked straight into the gap it exposed. Two live executions, two holes (the environment handoff; the in-flight cell); both found by the operator watching the pane, neither by a rung.

1. **Overwrite and COMMIT the state pointer** (`docs/<role>-state.md`; the orchestrator writes its `docs/orchestrator-handoff-<date>.md` instead). The successor reads HEAD; uncommitted = a handoff to nobody. *Inversion:* announce-before-commit → the successor bootstraps off a stale HEAD. **Act 1 records every AUTHORITY granted by cell message — declared envelopes, scope grants, mid-round fix authorizations, a fourth-round authorization — because a grant is STATE and a cell message is not a record** (coa-chess, its first end-to-end rollover 2026-09-07: the outgoing orchestrator found three grants that existed nowhere durable and would have died with their cells). **Act 1 carries POINTERS and STATE, never a plan/code fact from memory (2026-09-08, three corrections to one orchestrator handoff inside a day):** the ahead-of-origin count (34, corrected to 71 at `a102fcf1`); a sequence line the merge itself had made unrunnable (replaced at `e50c8ec1`); an untracked file left as an open question. Every in-flight fact in the pointer is RE-VERIFIED AT WRITE TIME and carries its METHOD (`git status -sb` at the time, `git worktree list`, `PRAGMA user_version`) so the successor can re-run it rather than inherit it; a term of art is cited by pointer to its definition (§5.1's sibling rule). A handoff is read by a seat with no memory of the session — the facts it states are the only ones the successor has.
2. **Post the rollover announcement (`status`, to the other two roles) and STOP DRAINING — `peek` only from here.** **The B-14 Stop hook's "drain now" instruction is VOID for an outgoing generation:** obeying it swallows the successor's first mail. *Inversion:* launch-before-announce → two drainers for a window.
3. **`TaskStop` the inbox Monitor.** With it gone nothing can wake the old session again. *Inversion:* launch-before-monitor-off → the old session wakes into the successor's mail.
4. **LAST ACT — run the launcher for your OWN role in FRESH mode** (never `-Resume`: resume reopens the context being left), then go idle; the operator closes the old pane at leisure. The command is the comms GUI's own fixed argv, run from the repo root: `powershell -NoProfile -File scripts/start_directors.ps1 -Role <role>`. **Run it once with `-DryRun` first** and read the printed command line (preflight verifies the CLI flags; a preflight failure after the monitor is gone leaves a seat empty), then run it for real.

**A SELF-LAUNCH IS AN ENVIRONMENT HANDOFF, NOT JUST A PROCESS SPAWN (found on RD's first live rollover, 2026-09-07, within the hour; coa-chess verified the mechanism at its seat, CHARC reproduced it here).** A running session's shell carries ten `CLAUDE*` markers (`CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_SESSION_ID`, the messaging socket + token, `CLAUDE_PID`, …); `Start-Process` inherits them; a child `claude` that sees them starts with **transcript saving OFF** (no resume, nothing for `cell_depth.py` to read) and the PARENT'S messaging identity. The successor RD launched in exactly that state. Fix (`start_directors.ps1`, `Build-LaunchCommand`): the spawned shell scrubs the markers BEFORE invoking `claude`, on both vehicles; probe-verified from a live session (control child: 10 markers; scrubbed child: 0) and pinned by test. **Verify what a child inherits with a probe window before trusting any launch vehicle** — the GUI path was clean only because the GUI's process had no session environment to leak.

Two properties to know before relying on it: the Stop hook and the Monitor cover COMPLEMENTARY windows (mid-turn vs between-turn arrivals) and act 2 deliberately voids one of them, so the void must be stated where the outgoing generation reads it (each bootstrap carries it). And the in-session launch is **proven by the GUI path and by `-DryRun`, not yet by a live rollover from a session** — the first real rollover on each seat is its test and is reported in the announcement's successor message. Docs that embed the launcher command are edited with the file-editing tool, not a shell heredoc carrying the command as text (a safety classifier blocked exactly that, on both projects, the day this landed).
