### The load-bearing consequence for the design

The CLI **already** maps the collision to a distinct exit code (`blocked → 2`). BUT **click's own `UsageError` also exits with code 2** (a malformed wrapper invocation — a bad flag, a typo in the registered action — exits 2). So the existing `exit 2` is **ambiguous** (collision vs. wrapper-coding-bug). Relying on bare `exit 2` for the graceful-skip control-flow would be exactly the "string-matching-grade" fragility the brief §3 warns against, one level up. **The resolution (Task 2) is a dedicated, unambiguous exit code behind an opt-in `--skip-if-running` flag** — an explicit integer contract, no stdout string-matching, backward-compatible with the existing `exit 2` default.

## §1 Design overview

Four deliverables, no schema, no new `swing/` module, no dependency:

1. **`swing/cli.py` affordance** — add `--skip-if-running` to `pipeline run` (existing-module edit, sub-tripwire). Maps the `blocked` `RunResult` to a **dedicated exit code 75** + an ASCII skip message. Default (flag absent) behaviour is **unchanged** (`blocked → 2`). *(Task 2, TDD.)*
2. **PowerShell wrapper** `scripts/run-weeknight-pipeline.ps1` — absolute-path invocation of `swing pipeline run --skip-if-running`, the C2 exit-75→graceful-skip mapping, the C4 always-one-line scheduler result log, ASCII-only output, a pre-flight for the exe-not-found / repo-missing class. *(Task 3–5, unit-testable where the mapping logic lives; witness-verified end-to-end.)*
3. **Idempotent task register/unregister scripts** `scripts/register-weeknight-task.ps1` + `scripts/unregister-weeknight-task.ps1` — `Register-ScheduledTask -Force` (update-in-place), operator-account principal, Start-in = MAIN repo root, "Do not start a new instance", "start ASAP after missed start". Operator-run at the witness. *(Task 6, witness-verified — NOT unit-mocked.)*
4. **Runbook** `docs/runbooks/weeknight-pipeline-scheduled-task.md` — the schedule, pause/resume/unregister, and the collision / stale-lease / token-degrade playbook. *(Task 7.)*

**Control-flow signal chain (explicit, no string-matching):**
`acquire_lease` → `ConcurrentRunBlockedError` → `RunResult(state="blocked")` → CLI `--skip-if-running` → **exit 75** → wrapper `if $LASTEXITCODE -eq 75` → one "SKIP" result line + **wrapper exits 0** (task stays green).

## §2 The C1–C6 binding conditions — explicit design (dedicated section for CHARC's confirm)

This section is the CHARC plan-stage confirm surface. Each condition names its concrete design decision + where it lives.

### C1 — Launch context (operator account, absolute paths, Start-in = MAIN repo root)
- **Principal:** the register script sets the task principal to **the invoking operator's OWN account, resolved from the live logon token — NOT a hand-assembled env string.** Use `[Security.Principal.WindowsIdentity]::GetCurrent().Name` (returns the correctly-qualified `COMPUTER\user` on a non-domain box or `DOMAIN\user` on a domain box; a hardcoded `"$env:USERDOMAIN\$env:USERNAME"` is WRONG on non-domain/Microsoft-account machines where `$env:USERDOMAIN` is the computer name and the stored identity may need `.\user`). Pass that resolved name to `New-ScheduledTaskPrincipal -UserId`. **NEVER** `SYSTEM`/`NT AUTHORITY\*`/a service account — an explicit guard in the register script refuses to register if the resolved SID is a well-known service SID (`S-1-5-18/19/20`). *(Rationale: a foreign `USERPROFILE` resolves a different home-anchored DB — the #5 vector; the 19-B guard would suppress-and-warn but the run would be useless.)* The registered principal is then witness-verified (§5 stage a.2b) against the operator's real profile — the plan does not trust the resolved string blind.
- **Absolute paths everywhere:** the wrapper takes `-SwingExe` and `-RepoRoot` params whose **defaults are hardcoded absolutes** (`C:\Users\rwsmy\AppData\Roaming\Python\Python314\Scripts\swing.exe`, `C:\Users\rwsmy\swing-trading`). No bare `swing` on PATH; no PATH-dependent resolution (a scheduled-task PATH is not the interactive PATH). The register script's action invokes `powershell.exe` by absolute path with `-File <absolute wrapper path>`.
- **Start-in = MAIN repo root:** the register script sets `-WorkingDirectory 'C:\Users\rwsmy\swing-trading'` on the action, and the wrapper does `Set-Location $RepoRoot` as belt-and-suspenders. **Never a worktree.** *(The register/unregister scripts carry an explicit comment: run these from the MAIN checkout only.)*
- **DETERMINISTIC data-root pin (the real C1 guarantee — the #5 vector, closed at the strongest lever):** the pipeline resolves its DB / logs / exports / finviz-inbox via `_resolve_path(raw, home, project_root)` where **`project_root = config_path.parent.resolve()`** (`config.py:642`) — i.e. the DATA/artifact root derives from the `--config` PATH, NOT from cwd. So the wrapper invokes with an **absolute `--config C:\Users\rwsmy\swing-trading\swing.config.toml`** (a `-ConfigPath` param default). This PINS `project_root` to the MAIN tree DETERMINISTICALLY — cwd, Start-in, and any PATH/editable-install ambiguity cannot divert the project-internal artifact roots (exports/, finviz-inbox). The home-anchored roots (`~/swing-data/*`) still resolve via `USERPROFILE`, which is why the operator-account principal (above) is the paired guarantee. *(This is the 19-B "one config-derived launch-context root" made explicit at the strongest available lever — the absolute config path — rather than left to cwd inference.)*

### C2 — Collision = graceful skip
- `ConcurrentRunBlockedError` → `RunResult(state="blocked")` → CLI `--skip-if-running` → **exit 75** → the wrapper maps 75 to a "SKIP" result line + **exit 0** (NOT a task failure — no red icon on a benign manual-run collision).
- Task Scheduler policy: **`-MultipleInstances IgnoreNew`** ("Do not start a new instance") in the register script — a belt around the app-level lease skip (two independent layers: the scheduler won't double-launch; if a *manual* run is live, the app-level lease returns blocked→75→graceful).
- **The task NEVER auto-`force-clear`s.** Stale-lease recovery stays the existing operator `pipeline force-clear` path (documented in the runbook). An unattended auto-force-clear could kill a live manual run — **explicitly OUT of scope**; the wrapper contains no force-clear call.

### C3 — No interactive auth reachable (verified)
- **No new code required** — the existing Phase 15 / 18-H hardening already guarantees it: the non-setup Schwab paths (`construct_authenticated_client`, `force_refresh`) are protected by `_assert_v3_tokens_db_loadable_or_raise` (reads the DB + rejects old-format/stale/key-loss BEFORE construction) + `call_on_auth=_raise_on_auth` + `open_browser_for_auth=False`; the market-data ladder falls through to yfinance on Schwab failure; domain writes are sandbox/production-gated. No `input()`/browser hang is reachable headless. The 7-day refresh-TTL expiring mid-week is EXPECTED steady-state; the yfinance degrade IS the design; `swing schwab status` + the 18-H.1 token-health monitor surface the staleness.
- **Discharge = citation (all failure modes) + a MANDATORY discriminating WITNESS (the representative branch).** The BINDING C3 condition is "no interactive auth reachable" = **NO HANG / no headless `input()`/browser prompt**. The existing `_assert_v3_tokens_db_loadable_or_raise` covers ALL token-failure modes — absent, old-format, stale-refresh, undecryptable/key-loss — by RAISING before construction (Phase 15/18-H tested; the CITATION covers the branches the witness does not individually re-exercise). The witness (§5 stage a.4) exercises the **absent-DB branch as the representative discriminating fire** (the highest-signal, easiest-to-stage case); the other branches rely on the cited hardening, not a per-branch witness. **The C3 PASS criterion is no-hang** (the run terminates in the normal duration, never at the ExecutionTimeLimit; no interactive prompt reachable). The EXPECTED outcome is completion-via-yfinance (the market-data ladder falls through to yfinance on Schwab failure — brief §0); a clean fast-FAILURE without a hang would ALSO satisfy the auth-safety condition but would flag a SEPARATE yfinance-fallthrough regression to investigate (not a C3 failure). A normal-run-with-a-live-token fire does NOT satisfy C3 — the hazard is exercised, not assumed away.
- **MANDATORY negative guard test (not optional) — because C3 is broader than "no hang."** A regression that briefly opens a browser / prompts and THEN fast-fails-or-degrades could still pass the runtime no-hang witness. So C3's discharge also includes a **mandatory discriminating unit test** asserting the pipeline's non-setup Schwab construction path (`construct_authenticated_client`, the path the market-data ladder uses under the scheduled task) is invoked with `open_browser_for_auth=False` AND the raising non-interactive `call_on_auth` (`_raise_on_auth`) — so any future change that reintroduces an interactive/browser auth in the UNATTENDED path fails the suite. This static wiring assertion (a regression tripwire tied to THIS arc's new unattended launch context) COMPLEMENTS the runtime no-hang witness; together they cover "no interactive auth reachable" (the wiring can't request it; the run doesn't hang). The executing implementer locates the exact construction site; the test asserts the two non-interactive params at that call. TDD'd (Task 2 cluster).

### C4 — Observability = the existing spine + a minimal scheduler-level floor
- The in-app spine already covers a completed-but-unhealthy run: `pipeline.log`, the `pipeline_runs` ledger, the 18-D/18-E monitors, the GUI stoplights, the lease-verified RED push. **No new monitoring machinery.**
- The wrapper adds **one appended result line per fire the wrapper survives to write** to a fixed absolute path (Task 5) — the "scheduler-level floor" for the class that never reaches in-app logging (exe-not-found, config-missing, interpreter failure, a launch exception before Python starts). One line, no machinery. Outcomes: OK / SKIP / FAIL / ERROR / **TIMEOUT**. *(Design note surfaced for CHARC: the plan writes the line on EVERY outcome the wrapper reaches, not only the never-logged class, because a single always-appended tail-able line is strictly more useful to the witness and still "minimal, one line, no new machinery." If CHARC prefers the strict "only-the-never-logged-class" reading, gate the line on non-zero/launch-failure only — a one-line change. Recommendation: always-one-line.)*
- **Hang handling — a wrapper-enforced timeout, so a hang IS logged (not silently scheduler-killed).** A naive `& $SwingExe ...` that hangs would let Task Scheduler's outer `ExecutionTimeLimit` (2h, §4) TERMINATE the wrapper — after which PowerShell never resumes to append a line, so the most important unattended failure (a hang) would leave NO result line. **Fix:** the wrapper runs `swing.exe` as a child it can bound with its OWN shorter timeout (`-RunTimeoutMinutes`, default e.g. 30 — well above the normal ~2–3 min run, well below the scheduler's 2h): if the child does not exit in time, the wrapper KILLS the whole PROCESS TREE, appends a **TIMEOUT** line, and exits non-zero. **The kill MUST be process-tree, not `$p.Kill()`:** `swing.exe` is a console-script LAUNCHER that spawns the real `python.exe` as a child; killing only the launcher would ORPHAN the python process (still running, still holding the lease, still writing) — defeating both the C4 timeout bound and the C2 collision guarantee. The wrapper uses **`taskkill /T /F /PID $p.Id`** (`/T` = terminate the descendant tree, reaching the python child) invoked by its **ABSOLUTE path** (`"$([Environment]::SystemDirectory)\taskkill.exe"` — C1 forbids PATH-dependent resolution, and the kill path is load-bearing) — OR, as an alternative the executing implementer may prefer, invoke `python.exe -m swing.cli` DIRECTLY (an absolute interpreter path, no launcher indirection) wrapped in a Windows Job Object. `taskkill /T /F` is the recommended default (simplest, keeps the absolute-`swing.exe` invocation). **The wrapper CHECKS the kill succeeded** (`$LASTEXITCODE` after `taskkill` — `$ErrorActionPreference='Stop'` does NOT throw on a native command's nonzero exit): on a failed kill the python child may still be alive holding the lease, so the wrapper writes a distinct **TIMEOUT-KILL-FAILED** ERROR line (louder than a plain TIMEOUT) so the operator knows to `pipeline force-clear` a possibly-live orphan. The scheduler's `ExecutionTimeLimit` stays only as an OUTER backstop for the (now much rarer) case where the WRAPPER ITSELF hangs — that residual case is recorded in **Task Scheduler's own run history / `LastTaskResult`** (the runbook, Task 7, points there). So the "one line per fire" guarantee holds for every case the wrapper survives; a wrapper-level hang is covered by Task Scheduler history, not a false in-file guarantee.

### C5 — Holiday/weekend posture: no special logic required
- A holiday/weekend fire is a harmless same-asof re-prep (brief §0 evidence: runs 118/119/120 all `data_asof=2026-07-02`). The trigger is Mon–Fri, so a *holiday* on a weekday is the nominal re-prep case, and it is harmless. **No session-aware skip is built.**
- **`-StartWhenAvailable` OFF-WINDOW catch-up — accepted and documented (NOT actually "Mon–Fri only").** With `-StartWhenAvailable` ON + Interactive logon, a MISSED 17:30 fire (machine off/asleep, or not logged on) runs LATER when the machine next becomes available / the operator next logs on — which CAN be a Saturday, a Sunday, or a weekday morning. So the job is NOT strictly constrained to weeknight-evening fires. **This is ACCEPTED because it is harmless** by the same C5 argument: a catch-up fire is a same-asof re-prep (the lease + collision-skip + the 19-B guard all still apply); it just re-preps the last-completed-session's data. The runbook (Task 7) documents this explicitly so an off-window catch-up run in `weeknight-task.log` is not misread as a fault.
- *Optional POLISH (operator's call at plan review):* a session-aware skip could be added later (the wrapper checks an NYSE-session helper and no-ops on a non-session day, suppressing the off-window catch-up). Correctness does not depend on it; NOT in this plan's scope unless the operator requests it. If the operator instead prefers NO catch-up at all, set `-StartWhenAvailable` OFF at registration (a §4 param) — then a missed fire is simply skipped until the next scheduled weeknight.

### C6 — The 19-B floor is a backstop, not the design
- Build the task CORRECT per C1 (operator account, absolute paths, Start-in = MAIN root). The 19-B anchor-consistency / lease-or-silent / broken-context guard is the net UNDERNEATH — the plan does not lean on it. No 19-B code is touched.

## §3 Resolved design questions (brief §3)

1. **Exit-code mapping for `ConcurrentRunBlockedError` through click — CHOSEN: a dedicated exit code behind an opt-in flag, over string-matching.**
   - Add `--skip-if-running` to `pipeline run`. WITH the flag, `state == "blocked"` → `click.echo("Pipeline run skipped: another run is already in progress (…).")` + `ctx.exit(75)`. WITHOUT the flag → unchanged (`exit 2`). `failed → 1` and success `→ 0` are unchanged in both modes.
   - **Why 75 (not 0, not 2, not 3):** (a) `0` would make a skip indistinguishable from a real completed run at the exit-code level — the wrapper could not write a distinct SKIP line without stdout string-matching; (b) `2` collides with click `UsageError` (ambiguous); (c) `75` is BSD `EX_TEMPFAIL` ("temporary failure; retry later") — semantically exact for "a run is in progress," and outside the {0,1,2} click-reserved band. The wrapper checks `-eq 75` explicitly (an integer compare, not a string match) and translates it to its own exit 0 so the TASK stays green. This is the "explicit contract over string-matching" resolution, one contract layer deeper than the brief asked for.
   - **Backward compat:** the default path (`exit 2` on blocked) is preserved, so the existing behaviour + any test asserting it is untouched; the flag is purely additive.

2. **`Register-ScheduledTask` idempotency — CHOSEN: `Register-ScheduledTask -Force` (update-in-place, single call), over unregister-then-recreate.** `-Force` creates-or-replaces in ONE call, so re-running the register script after a definition edit is idempotent and reproducible. *(No atomicity guarantee is claimed — Task Scheduler cmdlet replace-atomicity is not established and is NOT load-bearing here: re-registration is an operator maintenance action, never concurrent with a scheduled fire, so any momentary replace window is harmless. The one-call form is preferred over unregister-recreate simply for fewer operations + no explicit two-step teardown-then-rebuild.)* The separate `unregister-weeknight-task.ps1` is for teardown only (`Unregister-ScheduledTask -Confirm:$false`), NOT part of the update path.

3. **S4U environment realities — V1 DECISION: `Interactive` ("run only when logged on") is the SUPPORTED design; S4U is explicitly DEFERRED, not merely "verify-at-witness."** Under S4U ("run whether logged on or not"), Windows performs a network/batch logon that does **not** load the full user profile the way an interactive logon does — `USERPROFILE`, `APPDATA`, `HOME` and the editable-install Scripts dir can resolve differently or be absent. Because the pipeline resolves its DB / logs / exports through the HOME-anchored config (`config.py:_resolve_path` → `$USERPROFILE\swing-data`), S4U can silently send the app to a DIFFERENT (foreign/empty) data root — the exact #5 vector. "Verify at the witness" is NOT sufficient DESIGN for a path that can corrupt the data root. **So V1 ships `Interactive` as the design** (full profile loaded, matching the environment the editable install + home-anchored DB were validated under; the operator's box is a single-user personal machine that is normally logged on — Interactive is a fit, not a compromise). **S4U is DEFERRED and the V1 register script REFUSES it outright** (a hard error, not a warning) — enforcing the C1/C6 boundary in code, not prose. S4U may be adopted later ONLY after EITHER (i) the app is changed to resolve its data roots from an EXPLICIT config/env the wrapper sets deterministically (not HOME inference) — a separate, out-of-scope change — OR (ii) a discriminating S4U-context witness proves the DB/exports/ledger land in the operator's MAIN tree; either path is a FUTURE register-script change that ADDS the S4U branch behind that validation. **In V1 the register script hard-refuses `-LogonType S4U`** with an actionable error naming the precondition (it does NOT create an S4U task on a warning). The `-LogonType` param accepts only `Interactive` in V1. *(The wrapper's OWN critical paths depend on NO environment variable — hardcoded absolute param-defaults — so the wrapper is S4U-safe; the residual S4U risk is entirely the pipeline's HOME-anchored data root, which is why S4U is refused at the register boundary.)*

4. **Where the scheduler-level result line lives — CHOSEN: a fixed absolute path co-located with the in-app logs, `C:\Users\rwsmy\swing-data\logs\weeknight-task.log`** (a wrapper `-ResultLog` param default). Co-located with `pipeline.log` (one place the operator tails), but written by the wrapper to a **hardcoded absolute** path — NOT config-derived (config-missing is one of the failure classes it must survive), and NOT `$env:USERPROFILE`-derived (deterministic under any logon type; if USERPROFILE were wrong under S4U, a config-derived path would misdirect the very diagnostic line meant to reveal the misconfiguration). The wrapper `mkdir -Force`s the parent before appending.

## §5 The two-stage operator witness (brief §4.4 — the arc closes on stage b)

The registration script is verified **at the witness with a real scheduled fire**, NOT unit-mocked. Explicitly: there are no fabricated registration unit tests asserting nothing real (Task 6 ships no `*.Tests.ps1` for the register/unregister scripts; their correctness is a real-fire property).

- **Stage (a) — register + a one-off NEAR-TERM real scheduler-context fire + a deliberate collision demo.** The operator: (1) runs `register-weeknight-task.ps1` (as himself); (2) triggers a near-term real scheduler-context fire — **by re-running `register-weeknight-task.ps1 -IncludeOneOffAt <a few min out>` (Task 6), which SCRIPTS a one-off trigger ALONGSIDE the canonical Mon–Fri 17:30 weekly trigger** (no manual Task Scheduler mutation; clobbering the weekly trigger would mean the stage-(b) weeknight fire never happens) — and lets **Task Scheduler launch it** (a real scheduler-context launch — NOT right-click "Run now", NOT a manual shell invocation of the wrapper); verifies the run completes, artifacts land in the MAIN tree correctly, the `pipeline_runs` ledger shows the row, and the `weeknight-task.log` shows one "OK" line.
  - **(2c) Schedule-integrity RESTORE before stage (b):** after the stage-(a) demos, the operator **RE-RUNS `register-weeknight-task.ps1`** (idempotent `-Force`) to guarantee the task holds EXACTLY the canonical Mon–Fri 17:30 weekly trigger (any transient one-off trigger removed) — then confirms `(Get-ScheduledTask <name>).Triggers` shows only the weekly trigger. This is MANDATORY: stage (b) cannot close the arc if the live schedule was left in a test state.
  - **(2b) Principal verification (C1):** after registering, the operator confirms the registered principal is his ACTUAL profile AND the Interactive logon type — `(Get-ScheduledTask <name>).Principal.UserId` matches `[Security.Principal.WindowsIdentity]::GetCurrent().Name`, `(Get-ScheduledTask <name>).Principal.LogonType` is `Interactive` (NOT `S4U`/`Password`/`Group`), and the completed run's DB/exports resolved under HIS `%USERPROFILE%\swing-data` (not a foreign/empty home). This is the discriminating check for the "operator account" binding.
- **(3) Collision demo — DETERMINISTIC, HEARTBEAT-KEPT lease holder (not a racy manual run, not a bare sleep).** A normal manual run holds the lease for only a short, nondeterministic window, so the demo must NOT depend on catching that window. **AND a bare `acquire_lease(...) + time.sleep(N)` is WRONG:** `acquire_lease` stamps `lease_heartbeat_ts=now` but does NOT keep heartbeating; the block test is `age <= block_threshold_seconds` where `block_if_running_within_seconds=120` (`config.py:163`), so a sleep past ~120s ages the lease OUT of the blocking window and the demo silently stops exercising the collision (a false pass/fail on timing). **The demo therefore uses the SAME heartbeat mechanism a real run uses** — `swing.pipeline.heartbeat.Heartbeat` (interval 30s, `config.py:162`) started against the held lease so it stays fresh regardless of how long the operator waits for the scheduled fire. A throwaway snippet (documented in the runbook, §6 Task 7), sketch:
  ```python
  from swing.config import load
  from swing.pipeline.lease import acquire_lease
  from swing.pipeline.heartbeat import Heartbeat
  import time
  cfg = load("swing.config.toml")
  L = acquire_lease(db_path=cfg.paths.db_path, trigger="manual",
                    data_asof_date="2026-07-02", action_session_date="2026-07-03")
  hb = Heartbeat(lease=L, interval_seconds=cfg.pipeline.heartbeat_interval_seconds); hb.start()
  try:
      time.sleep(240)          # outlives block_if_running_within_seconds; stays FRESH via hb
  finally:
      hb.stop()
      # DO NOT release as "complete" — that would fabricate a false-green completed
      # run in the production pipeline_runs ledger (the observability spine). Release
      # to force_cleared with an explicit marker so the row is unambiguously a demo
      # artifact, not a real run. (state CHECK allows force_cleared — migration 0003.)
      L.release(state="force_cleared",
                error_message="19-C collision-demo synthetic lease; no pipeline executed")
  ```
  While the snippet holds the fresh-heartbeat lease, let the scheduled task fire → verify exit 0 + a "SKIP" line + no red task icon + the held lease row unaffected. (This exercises the SAME `ConcurrentRunBlockedError` path a real manual overlap would — a fresh heartbeat inside the block window — but on the operator's schedule, not a race.) **The demo runs against the PRODUCTION DB** (the held lease must be in the same DB the scheduled task reads, else no collision — so a disposable-DB isolation would defeat the demo); the `force_cleared` + marker release is what keeps it from polluting the ledger with a false completed run. *(Run from the MAIN checkout via `python -m swing.cli`-equivalent env, or a plain `python` with the repo on `sys.path`; the editable install makes `from swing...` resolve the MAIN tree.)*
