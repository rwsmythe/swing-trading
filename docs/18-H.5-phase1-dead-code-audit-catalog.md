# 18-H.5 Phase 1 — dead-code-hardening AUDIT catalog

**Authored:** 2026-06-16 by the 18-H.5 Phase-1 implementer (dispatch brief
`docs/18-H.5-dead-code-hardening-audit-dispatch-brief.md`, CHARC spec
`f3b95d3e`). **Read-only audit — NO production code shipped this phase.**
**Base:** `516c24f3` (main HEAD at dispatch).

A "dead-code-hardening" candidate = a defensive branch in a READER / CONSUMER /
MONITOR that guards a state an upstream constraint VERIFIABLY prevents (a schema
`CHECK` / `UNIQUE` / `NOT NULL` / FK, a migration, or a constrained writer/repo),
so the branch is UNREACHABLE on our own constrained DB. The classification:

- **(A) redundant** — a GENERAL handler already covers it → the per-case branch is removable.
- **(B) per-case → general** — N per-case branches that should collapse to ONE general graceful-degrade + LOGGING.
- **(C) NOT dead — KEEP** — the constraint is weaker than assumed, OR a non-schema write path exists, OR it guards a genuinely-unconstrained input (missing/pre-schema table, absent/corrupt FILE, future-dated/out-of-contract artifact, any non-schema-prevented reachable vector). **C is the DEFAULT** — A/B ONLY with a verified, READ constraint citation.

(candidate A-1).

## Candidate A-1 — `reconcile.py` 409 guard: the `ambiguity_kind is None` disjunct

### (a) file:line + the defensive branch

Two route sites (the GET resolve-form 409 and the POST state-guard 409), both an
identical short-circuited OR:

`swing/web/routes/reconcile.py:331-334` (GET):
```python
if (
    disc.resolution != "pending_ambiguity_resolution"
    or disc.ambiguity_kind is None
):
    return _render_error(request, status_code=409, error_kind="already_resolved", ...)
```

`swing/web/routes/reconcile.py:820-824` (POST, "Step 4b — state guard"):
```python
if (
    disc.resolution != "pending_ambiguity_resolution"
    or disc.ambiguity_kind is None
):
    return _render_error(request, status_code=409, error_kind="already_resolved", ...)
```

The module docstring (`reconcile.py:16-19`) already flags it: "`disc.ambiguity_kind
is None` (defensive — schema CHECK in migration 0019 normally forbids the second
case, but covered for hardening)."

### (b) the CITED upstream constraint (READ + VERIFIED)

`swing/data/migrations/0019_phase12_bundle_c_auto_correct_reconciliation.sql:135-147`
— the bidirectional cross-column CHECK on `reconciliation_discrepancies`:
```sql
CHECK (
    (ambiguity_kind IS NULL
        AND resolution NOT IN ('pending_ambiguity_resolution','operator_resolved_ambiguity'))
    OR
    (ambiguity_kind IS NOT NULL
        AND resolution IN ('pending_ambiguity_resolution','operator_resolved_ambiguity'))
)
```
This enforces the biconditional: `ambiguity_kind IS NOT NULL` **iff** `resolution
IN (pending_ambiguity_resolution, operator_resolved_ambiguity)`. Therefore, in the
exact state the OR's second operand can be reached (first operand FALSE →
`resolution == 'pending_ambiguity_resolution'`), the CHECK GUARANTEES
`ambiguity_kind IS NOT NULL`, so `disc.ambiguity_kind is None` is always False.

Read-path verified faithful: `swing/data/repos/reconciliation.py:102`
(`ambiguity_kind=row[19]`) is a pure pass-through — the reader does NOT manufacture
a `None` (no `or None` / default), so the dataclass field carries the true column
value. **Unlike FKs, SQLite CHECK constraints are NOT disablable by any PRAGMA**
(`foreign_keys=OFF` does not affect CHECKs) — so a normal INSERT/UPDATE cannot
bypass this constraint. The `disc.ambiguity_kind is None` sub-clause is genuinely
unreachable on a constrained write path.

### (c) classification: **(A) redundant**

The `ambiguity_kind is None` disjunct is dead given the verified CHECK. It is fused
into a single boolean OR whose FIRST disjunct (`resolution !=
'pending_ambiguity_resolution'`) IS the reachable, general "already resolved /
wrong state" 409 handler — i.e. the safety net is already present and general.
Removing the dead disjunct removes a per-case branch while leaving the general 409
intact (the corollary's positive half is satisfied for free).

**Residual-vector note (why this is the borderline of A vs C):** the only ways to
reach `ambiguity_kind is None && resolution == pending` are NON-schema-prevented:
(1) a manual DB edit, or (2) a future migration relaxing the CHECK. Per the C-default
discipline these are the standard escape hatches. The recommendation lands at A
because (i) the CHECK is verified and CHECKs are un-disablable, (ii) the general
409 net stays, and (iii) the disjunct adds no graceful-degrade value beyond the net
it already shares. **CHARC/operator call:** keep as a belt-and-suspenders (C) OR
remove the dead disjunct at both sites (A). If removed, the Phase-2 discriminating
test seeds a `pending_ambiguity_resolution` row via the CHECK-enforced writer and
proves the `is None` state is unconstructible, while the resolution-mismatch 409
still fires for a genuinely-wrong-state row.

## C candidates (NOT dead — KEEP)

### C-1 — `reconcile.py` builder precondition assert (`view_models/reconcile.py:764`)

(a) `swing/web/view_models/reconcile.py:764-768`:
```python
if disc.ambiguity_kind is None:
    raise ValueError("discrepancy has no ambiguity_kind; cannot render Tier-2 resolve form")
```
(b) Same migration-0019 cross-column CHECK as A-1 (verified above). The value IS
schema-prevented in the pending state.
(c) **C (KEEP).** Distinct from A-1 in NATURE: this is a deliberate
caller-contract ASSERTION (docstring §742-747: "Route handler MUST verify these
BEFORE invoking the builder ... Builder raises ValueError defensively ... to
surface a logic bug at the caller"). It is a tripwire that surfaces a
route-bypass/refactor bug at the VM seam, not a per-case data-degrade branch.
Removing it would silently swallow a future caller that invokes the builder past a
bypassed route check. Keep as an intentional internal-invariant assert.

### C-2 — `policy.py` orphan-stamp fallback (`metrics/policy.py:69`)

(a) `swing/metrics/policy.py:65-72`: `read_at_trade_time_policy` — if
`policy_id_stamp` resolves to no row (`get_policy_by_id(...) is None`), fall back to
LIVE policy. Comment: "Orphan: stamp present but row missing. Defensive fallback ...
(FK SHOULD prevent in V1; still handled ...)."
(b) `swing/data/migrations/0017_phase9_risk_policy_and_reconciliation.sql:354-355`:
`ALTER TABLE trades ADD COLUMN risk_policy_id_at_lock INTEGER REFERENCES
risk_policy(policy_id) ON DELETE SET NULL`. Production connections enforce FKs
(`swing/data/db.py:95` `PRAGMA foreign_keys=ON`).
(c) **C (KEEP).** Three non-schema-prevented vectors: (1) the migration runner /
rebuild path explicitly toggles `PRAGMA foreign_keys=OFF` (`db.py:344`), opening a
window where the FK on this ALTER-added column is not enforced; (2) the FK action is
`ON DELETE SET NULL` (deleting a parent NULLs the child, handled by the NULL arm —
but the FK is the only orphan guard and it is the disablable kind); (3) manual DB
edits / production data-integrity edges (the comment's stated intent). Already a
GENERAL graceful-degrade (fall back to LIVE + `fallback_applied=True` annotation),
not a per-case branch — nothing to collapse even if it were borderline.

### C-3 — monitor "schema unavailable" branches (`tool_health.py` + `research_health.py`)

(a) `swing/monitoring/tool_health.py:41-46,176-184,452-459` and
`swing/monitoring/research_health.py:268-272` + every per-check `except
sqlite3.OperationalError` arm (e.g. `research_health.py:337-344, 806-813, 1012-1019,
1191-1198, 1263-1269`): on a "no such table"/"no such column" `OperationalError`,
degrade that check to a yellow "schema unavailable"; re-raise ANY other
OperationalError.
(b) The TABLES are created by migrations (e.g. `pattern_forward_observations`
migration 0022; `yfinance_calls` migration 0030; `weather_runs`; `pipeline_runs`).
(c) **C (KEEP).** A migration creates the table, but NO constraint guarantees the
table EXISTS on the connection the monitor is handed — a pre-migration / partially-
migrated / degraded / test DB is a genuinely-reachable unconstrained input (exactly
the "missing/pre-schema table" C class named in the brief). This IS already the
corollary's prescribed shape: ONE general degrade-gracefully + a yellow signal that
identifies the gap, with a narrow `_schema_unavailable` predicate that re-raises any
OTHER OperationalError (so it does not mask a real defect — the 18-E never-assume
posture).

### C-4 — research-monitor corrupt-data / shape-drift branches (`research_health.py`)

(a) The corrupt-JSON / non-dict-bar / malformed-`observation_date` / out-of-calendar
/ duplicate-`observation_date` / shape-drifted-manifest branches, e.g.
`research_health.py:363-381` (non-finite/None/non-numeric OHLC),
`research_health.py:507-553` (`_manifest_is_well_shaped`),
`research_health.py:859-942` (malformed/duplicate observation dates).
(b) Relevant write-side: the 18-B.1 OHLC write-barrier in
`swing/data/repos/pattern_forward_observations.py:insert_observation` (fail-loud on
non-finite OHLC), `observation_date TEXT NOT NULL` (migration 0022, NO format
CHECK), `UNIQUE(detection_id, observation_date)`.
(c) **C (KEEP).** Multiple genuinely-unconstrained vectors: (i) `observation_date`
is `TEXT NOT NULL` with **no format CHECK** — `date.fromisoformat` accepts
non-canonical forms and SQLite stores any text, so a malformed/non-canonical date is
NOT write-prevented (the code's own R1-MAJOR comment at lines 293-302 documents this
exact hole); (ii) the engine MANIFEST is a JSON FILE, not a DB row — entirely
schema-unconstrained (corrupt/partial/shape-drifted = the brief's "absent/corrupt
FILE" C class); (iii) these checks DETECT historical bad data that predates the
18-B.1 barrier (the accepted-historical 06-10 cohort) — they exist precisely because
the write barrier is recent and cannot retro-heal the backlog. This is the audit's
inverse-failure to avoid removing.

no constraint preventing it. The NaN/inf skip guards a genuinely-storable value (the

### Constraint-verification approach

For each candidate I (1) located the exact reader branch and quoted it; (2) found the
named/implied upstream constraint and **READ the actual migration `.sql`** (0017, 0019,
0020, 0022, 0030) to confirm the precise `CHECK`/`UNIQUE`/`NOT NULL`/FK text; (3)
verified runtime enforcement where relevant — `PRAGMA foreign_keys=ON` at
`swing/data/db.py:95` (and the `=OFF` rebuild window at `db.py:344`), and the SQLite
fact that **CHECK constraints have no disabling pragma** (so A-1 is genuinely
write-prevented while C-2's FK has a disablable window); (4) verified the read mapper
does not manufacture the guarded value (`reconciliation.py:102` faithful pass-through).
Where the constraint was weaker than the comment implied, or the input was a FILE /
empty-seed-table / un-CHECKed `REAL` / read-side TOCTOU, the candidate landed C.

## Phase-2 recommendation (for CHARC + operator)

Only **A-1** is a verified-dead schema-prevented branch. It is low-value to remediate
(2 fused disjuncts, the general 409 net already present) and carries the standard
manual-edit/future-migration residual. **Recommendation: either leave A-1 as
documented belt-and-suspenders, OR (Phase-2, if approved) remove the
`ambiguity_kind is None` disjunct at `reconcile.py:333` and `:823` only**, keeping the
`view_models/reconcile.py:764` assert (C-1, an intentional caller-contract tripwire)
and ALL C candidates untouched. No B-class collapse opportunity was found. The audit's
dominant finding is that the reader/monitor layer's defenses are correctly aimed at
genuinely-unconstrained vectors — the treadmill corollary (recipe §3) is already being
honored going forward, and there is very little legacy dead-code-hardening to retire.
